# Правила документации ANIMA

**Задача:** держать один понятный актуальный путь чтения без потери истории и экспериментальных отрицательных результатов. Объяснения — **по-русски**, имена классов, API, JSON-ключей, Stage, FAST/DEEP и других программных контрактов — в исходном написании.

## Источники истины и иерархия

| Вопрос | Каноническое место | Правило |
| --- | --- | --- |
| Что делаем до текущего выпуска? | [`roadmap.md`](roadmap.md) | Только следующие действия и открытые требования активного релиза |
| Что является v0.1? | [`versions/v0.1/contract.md`](versions/v0.1/contract.md) | Нормативный объём и R-01–R-10 |
| Что реально принято? | [`versions/v0.1/acceptance.md`](versions/v0.1/acceptance.md) | Evidence на названных SHA и явное решение владельца |

Имена каталогов чувствительны к регистру. **Не создавать одновременно `RESEARCH/` и `research/`**: это не переносимо на файловые системы с регистронезависимыми именами. Первичные материалы из прежнего `ROADMAP/` и `TESTING/` сохраняют оригинальные адреса, пока не подготовлена полная карта ссылок.

## Правило статусов

Различать **исторический Stage status**, существование **Implemented** модуля, **Validated Lab**, **release-accepted** gate и **Research/Planned**. Для каждого утверждения о PASS нужны конкретный сценарий и SHA. У Stage 7 `Planned` относится к полному Knowledge lifecycle, хотя его read-only deterministic boundary уже испытана. E4 isolated PASS не превращается в production authorization: отрицательный authority bypass и `NO-GO` остаются в обзоре.

Нельзя «обновить» результат `Inconclusive` или `Failed` без нового первичного evidence. Нельзя переименовывать `FastResult` Stage 5 в `CognitiveProposal` Stage 6 без объяснения перехода.

## Добавление и изменение материала

1. **Определить категорию**: релизный контракт, архитектура, история, исследование, методика, evidence или решение. Не писать одну и ту же нормативную формулировку в трёх местах.
2. **Привязать утверждения к источнику**: модуль, тест, snapshot, первичный report. Для ограничения рядом указать, что именно не проверялось.
3. **Не заменять историю будущим**: архивные фразы типа «P6 не начат» относятся к их исходной дате; в текущем обзоре добавить объяснение, не корректировать историю ради удобной картины.
4. **Сохранить совместимость**: перед перемещением файла проверить входящие ссылки, заголовки/anchors, тесты, raw fixture и Git paths; оставить совместимый указатель, пока ссылки не обновлены.
5. **Проверить текст**: названия на русском, без ложного общего PASS, с компактной навигацией и явными границами исполнения.

Для будущего релиза сначала утверждается объём и номер; лишь затем создаются новые requirements и acceptance. Новая гипотеза сама по себе не меняет `project.json`, существующий release contract или production path.

## Генерируемые блоки

[`scripts/update_docs.py`](../scripts/update_docs.py) читает **только** [`project.json`](project.json) и metadata `TV-*.md`; генерирует **только**:

| Страница | Маркер | Содержимое |
| --- | --- | --- |
| [`history/stages.md`](history/stages.md) | `AUTO:roadmap:START/END` | Историческая таблица Stage |
| [`TESTING/Results/README.md`](TESTING/Results/README.md) | `AUTO:results:START/END` | Индекс TV с Git snapshots |

`README.md` **не** получает автоматически `current_stage`; релизный статус нельзя выводить из исторического реестра. Не писать внутрь generated markers вручную и не создавать вторую сводку статусов, противоречащую `versions/`.

```bash
python3 scripts/update_docs.py
python3 scripts/update_docs.py --check
bash scripts/check.sh
```

`--check` только сверяет и **не** записывает файлы; обычная команда меняет содержимое между known markers после валидации *всех* целевых документов. Если результат неожиданно обновил файлы, сначала проверить `git diff` и upstream metadata. Утверждать, что генератор проверил исполняемую ANIMA, нельзя.

## Первичные свидетельства и редакционная дисциплина

- `docs/TESTING/Results/TV-NNNN.md`: после публикации не переписывать `date/result/snapshot`, не удалять негативные кейсы и `Не доказано`. Новая проверка — новая запись с точным SHA.
- Frozen schemas/fixtures, historic Git snapshots и raw logs **не** переопределять как `Passed` ради миграции документации.
- При расхождении не «исправлять» исходный эксперимент догадкой. Оставить рядом контекст `на момент SHA`, привести поздний источник и отдельно показать, какой факт относится к современной сборке.
- Секреты, пользовательские данные, `.venv`, `models/` и output runner не добавлять в Git. Документация — не бэкап памяти экземпляра.
- До изменения схемы или границ authority — отдельный ADR/миграционный план, negative tests и явное решение владельца.

## Правила безопасной миграции

Сначала построить карту «старый путь → новый канонический адрес → обратные ссылки → исходный SHA». Перемещать только при доказанной замкнутости ссылок; пока она не подтверждена, оставлять старый документ или совместимый указатель. Case-only rename каталогов требует проверки на Linux и регистронезависимой файловой системе.

**Критерии завершения:** нет broken local links и недостижимых страниц, нет двух конкурирующих нормативных контрактов, исходные TV и frozen fixtures нетронуты, полномочия описаны в исполняемом профиле, все `docs/` достижимы от [оглавления](README.md), static Check/pytest/CI проходят на окончательном чистом Git tree. Завершающий человеческий review читает три маршрута: *запуск v0.1*, *история Stage → текущая архитектура*, *эксперимент → решение → интеграция*.
