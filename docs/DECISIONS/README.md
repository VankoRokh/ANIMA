# Существенные решения

ADR сохраняет причину, выбор, последствия и открытые вопросы. **Accepted** —
принцип; реализация подтверждается в [архитектуре](../ARCHITECTURE/README.md).
Новый ADR нужен при изменении архитектуры или долгосрочных правил. Draft —
обсуждение, Superseded — заменённое решение, Rejected — отклонённое.
Рутинные правки остаются в Git.

## ADR-000

**Superseded by ADR-004.** 2026-10-12, первая система документации.
Контекст был в чатах; проект должен восстанавливаться без памяти помощника.
Выбраны docs основного репозитория, Markdown/Mermaid, VS Code и дополнительный
Obsidian. Основу сохраняем; раздельные карты/реестры и страницы статуса
увеличили стоимость обновления.

## ADR-001

**Accepted.** 2026-10-12, переносимость данных экземпляра.
Общий код и опыт имеют разное назначение. Код/документация версионируются вместе;
identity/state/history/memory/settings резервируются отдельно и переносятся
между совместимыми компонентами. Clone восстанавливает проект, продолжение
экземпляра требует его данных. Backup проверяется restore.

«Личность» — сохраняемые идентичность, опыт, предпочтения и правила обновления.
Файлы не доказывают сознание или непрерывность субъективного переживания.
Замена модели требует версии/конфигурации; те же данные не гарантируют одинаковое
поведение. Копирование отличается от переноса: правила ветвления, конфликты,
миграции и hot-unplug ещё не утверждены. Сменный носитель — долгосрочное направление.
Практика — [резервирование/восстановление](../OPERATIONS/README.md#резервирование).

## ADR-002

**Accepted.** 2026-10-12; источник — обсуждения 2026-10-07.
Fast обслуживает оперативную реакцию, Deep — тщательную обработку. Требование
допускает самостоятельный переносимый Fast с последующим обменом опытом.
Первый стенд — ноутбук; долгосрочно — полноценные узлы со своим хранением.

Цена: offline journal, синхронизация, совместимость данных/моделей и питание.
Разные названия не дают обучения, точности или непрерывности. Модели, latency/RAM,
транспорт, конфликты, резерв и распределение нагрузки требуют проектирования.
Контуры и проверки — [в планах](../ROADMAP/Research.md#fast-и-deep).

## ADR-003

**Accepted.** 2026-10-12; источник — обсуждение «Может ли ИИ страдать».
Единая глобальная награда/наказание не используется как единственный регулятор
личности. Учитываются цели, внутренние оценки и проверка результата. Локальное
подкрепление допустимо исследовать для конкретной периферийной задачи;
его результат передаётся наверх как наблюдение.

Это не отказ от метрик и не доказательство превосходства эмоций над RL.
Сначала задача, baseline простого управления, метрика, бюджет и сравнение
[EXP-003](../ROADMAP/Research.md#exp-003). RL необязателен.

[ведение документации](../OPERATIONS/README.md#ведение-документации).

## ADR-005

**Accepted.** 2026-10-26, архитектура Cognitive Memory для Stage 1.
Причина: Foundation сохраняет raw events и простую выбранную память, но не отделяет
подробную историю, компактный опыт и актуальное знание; без этого невозможно
проверяемо накапливать опыт, пересматривать выводы и строить ограниченный контекст
для будущих Fast/Deep без привязки к конкретной модели.

Выбрана трёхслойная долговременная модель: Event фиксирует произошедшее, Memory
хранит компактный смысл ограниченного эпизода, Knowledge — актуализированное
утверждение, выведенное из закрытого подтверждённого опыта. Entity является
устойчивым якорем, Relation — явной связью; Topic не хранится отдельной сущностью,
а формируется как временное представление связанной области данных.

Путь записи отделён от пути чтения. Memory Processor выполняет selection,
association, composition и knowledge evaluation; Context Builder через Retrieval
собирает ограниченный структурированный ContextBundle для конкретного consumer.
Оба слоя независимы от конкретной LLM. На Stage 1 используются deterministic
правила и объяснимые selection reasons; Deep/LLM, embeddings, vector/graph DB и
глубокая консолидация вводятся только после сравнения с baseline.

Raw Events остаются append-only в `events.jsonl`. Структурированные
Memories/Knowledge/Entities/Relations/History и состояние обработки хранятся в
локальном SQLite `memory.db`; FTS5 — baseline текстового retrieval. Одна универсальная
таблица relations предпочтительнее нескольких специализированных, пока benchmark
не покажет проблему производительности или целостности. Большие media-assets
хранятся отдельно и связываются references; полноценная media-обработка отложена.
Public IDs на Stage 1 используют type-prefix + UUIDv4: это сохраняет baseline
совместимым с Python 3.12+ без собственной реализации UUIDv7; порядок по времени
задаётся отдельными timestamp-полями, а не структурой ID.

Episodic Memory имеет lifecycle `OPEN/CLOSED/MERGED`: закрытый эпизод по умолчанию
не переписывается поздним опытом. Knowledge использует
`provisional/confirmed/challenged/superseded/rejected`; существенное противоречие
сначала переводит подтверждённое знание в `challenged`, а не молча заменяет его.
Происхождение должно проходить `Knowledge → Memory → Event`; существенные изменения
пишутся как компактная history/delta, а не как полные копии каждой версии.

Цена решения — более богатая схема данных, transactions, idempotent processing,
status transitions и необходимость контрольного corpus. Польза — независимость
памяти от моделей, объяснимый retrieval, сохранение истории противоречий и путь к
будущим Sleep/Fast/Deep без переписывания основы. Реализация и приёмка идут по
[Stage 1](../ROADMAP/README.md#stage-1); сознательно отложенные механизмы — в
[Research](../ROADMAP/Research.md#отложенные-механизмы-памяти-stage-1).

## ADR-006

**Accepted.** 2026-10-26, цели и регулирующее внутреннее состояние для Stage 2.
Причина: память уже умеет сохранять опыт и возвращать ограниченный контекст, но
система пока не имеет отдельного объяснимого слоя, который учитывает длительность
работы, недостаток информации, повторные неудачи и подтверждённый прогресс при
сравнении вариантов. Единая reward-функция для этого не используется по ADR-003.

Internal State является регулирующим входом в оценку вариантов, а не самостоятельным
источником решений: он не создаёт Goals или Candidates и не может подменить цель.
Первый deterministic baseline содержит четыре ограниченных значения `0.0..1.0`:
`fatigue`, `uncertainty`, `frustration`, `satisfaction`. Другие состояния вводятся
только после сценария и проверки, показывающих отдельную полезную функцию.

`fatigue` отражает накопленную стоимость активности: растёт от времени в `awake`
относительно настраиваемого рабочего периода и дополнительно от workload, а при
Sleep/recovery снижается. `uncertainty` отражает нехватку надёжной информации,
изменяется с учётом важности ситуации и качества подтверждения и сама по времени
не исчезает. `frustration` служит прежде всего защитой от зацикливания: повторные
неудачи одной стратегии усиливают прирост до ограниченного потолка, прогресс или
смена стратегии его снижают, а со временем значение восстанавливается к baseline.
`satisfaction` возникает только от проверенного прогресса/успеха; его прирост
учитывает важность и уменьшается при повторении однотипных успешных ситуаций,
после чего значение постепенно затухает. Его влияние на Choice намеренно слабее.

Все изменения проходят через детерминированный Transition Engine. История хранит
`before/delta/after`, время, cause/source, rule, reason и при необходимости
importance, repetition factor, elapsed time, Goal и Candidate. Прямое изменение
значений из других компонентов запрещено. Время инъецируется в тестах; временные
эффекты вычисляются лениво по elapsed time, чтобы restart или частота цикла не
создавали скрытый drift или двойной decay.

Правила и коэффициенты отделяются от живых данных. Версионируемая конфигурация
описывает диапазоны, baseline, временное поведение, веса и ограничения; текущие
значения, история переходов и lifecycle целей хранятся отдельно в transactional
SQLite `internal_state.db`. Goal имеет стабильный ID, source, priority, status,
критерий результата и причину завершения/отмены. Минимальный lifecycle —
`ACTIVE/BLOCKED/COMPLETED/CANCELLED`; self-generated Goals на Stage 2 не требуются.

Choice сравнивает заранее заданные Candidates: сначала оценивается соответствие
цели и свойства варианта, затем применяются ограниченные state modifiers.
Fatigue штрафует стоимость/усилие, uncertainty повышает ценность information gain
и осторожность к необратимому риску, frustration снижает привлекательность
повторения неудачной стратегии и поддерживает альтернативу, satisfaction даёт
небольшой бонус подтверждённо успешному продолжению. Ни один modifier не получает
неограниченного веса. Expression является односторонним отображением состояния
в тон/голос/визуальные сигналы и сам по себе не изменяет Internal State.

Цена решения — отдельное хранилище, причинная история и необходимость калибровать
коэффициенты. Точные числовые веса, длительность рабочего периода и кривые
роста/восстановления не считаются архитектурой: они остаются конфигурацией и
настраиваются по тестам. Польза — воспроизводимый baseline мотивационного слоя,
который можно измерять и расширять без привязки к LLM. Порядок реализации,
сценарии и Definition of Done — [Stage 2](../ROADMAP/README.md#stage-2).

## ADR-007

**Accepted.** 2026-10-26, архитектура Sleep orchestration и консолидации для Stage 3.
Причина: после Cognitive Memory и Internal State системе нужен отдельный режим,
который перерабатывает накопленный опыт пакетно и прерываемо. Сегодня основной
материал — текстовые Events/Memories/Knowledge, но в будущем Sleep должен работать
с дневными отчётами, аудио, видео, internal telemetry и другими тяжёлыми источниками.
Привязка оркестратора к тексту заставила бы переписывать Stage 3 при появлении media.

Sleep поэтому работает не с конкретным payload, а с `SourceRef` и bounded `WorkItem`.
Исходные Event/Memory/Knowledge/Asset остаются владельцами данных; Sleep хранит
ссылку, тип работы, processor/version, priority/cost hint, status и checkpoint.
Большой payload не помещается в Job или `sleep.db`; media/assets хранятся отдельно
и читаются processor-адаптером по chunks. Первый large-data proof выполняется на
synthetic source без реального многогигабайтного файла.

Persistent orchestration хранится отдельно в transactional `sleep.db`. SleepJob
имеет lifecycle `queued/running/checkpointed/interrupted/completed/failed`;
WorkItems и checkpoints переживают restart. Chunk считается завершённым только
после фиксации checkpoint и соответствующего локального результата. Если работа
создаёт effect в `memory.db`, две БД не объявляются одной физической транзакцией:
согласованность достигается stable operation/output IDs, idempotency и recovery.

Sleep scheduler формирует deterministic bounded workload по явным eligibility,
priority, cost и resource budget. Фиксированное расписание 16/8 или 12/12 не
является архитектурой. Первый cost model может быть категориальным; CPU/RAM/time
метрики уточняют его после измерений. Запрос wake имеет приоритет над продолжением
batch work и останавливает Sleep на безопасной checkpoint-границе, а не посреди
неатомарного изменения.

Processor является заменяемым адаптером и отделён от orchestration. Общий контракт
должен допускать разные source/work kinds, chunk processing, checkpoint state и
finalize. Первый обязательный processor — deterministic text `CONSOLIDATE`:
фильтрация eligible источников, детерминированные grouping/sorting/deduplication и
bounded derived result/report. Он не удаляет raw Events, не переписывает CLOSED
Memory и не подтверждает Knowledge сам по себе; изменения Memory/Knowledge проходят
через уже существующие lifecycle/evidence rules.

Приоритетный baseline использует raw Events/observations, CLOSED Memories с валидным
provenance и CONFIRMED Knowledge с evidence. Derived Sleep output имеет явное
происхождение и processor/version и не получает authority исходного наблюдения или
подтверждённого Knowledge автоматически. Каждый существенный результат должен быть
прослеживаем к фактическим источникам; missing provenance является ошибкой, а не
поводом создать непроверяемую «истину».

Reflection старого опыта, replay/counterfactual simulation и generative dreaming
считаются совместимыми будущими типами Sleep-work, но не входят в обязательный
Stage 3. Сейчас недостаточно длительной истории и контрольных данных, чтобы честно
проверить их полезность и точность. Любой будущий hypothetical result обязан быть
явно отделён от observation/verified knowledge. Deep/LLM также вводится только как
сравниваемый processor после deterministic baseline, а не как условие Sleep.

Цена решения — отдельное orchestration storage, processor contracts, checkpoints,
recovery protocol и дополнительные тесты large-data readiness. Польза — Sleep можно
расширять новыми data types и cognitive processors без замены scheduler/lifecycle;
длинная работа становится прерываемой, а история преобразований остаётся проверяемой.
Порядок реализации, проверки и Definition of Done — [Stage 3](../ROADMAP/README.md#stage-3);
отложенные cognitive механизмы — [Research](../ROADMAP/Research.md#когнитивный-сон).

## ADR-008

**Stopped for further development; cognition-specific parts superseded by ADR-009.** 2026-10-29. Изначально Accepted 2026-10-27 для Stage 4.

Причина: после Cognitive Memory, Internal State и Sleep системе нужен первый
проверяемый контур действий во внешней среде. При этом подключение готового
LLM-agent framework как владельца plan/execute loop скрывало бы работу уже созданных
Goals, Choice, Memory и recovery-механизмов и не позволило бы понять источник ошибки.
Stage 4 поэтому строил собственный agent runtime, а языковая модель оставалась
заменяемым компонентом.

Tool system использует собственный версионируемый контракт ANIMA с JSON-Schema
входа/выхода и системной metadata о side effects, reversibility, idempotency,
timeout и sandbox scope. Контракт концептуально совместим с MCP, чтобы позднее
подключать внешние MCP tools через adapter, но MCP не является внутренним ядром
Agent и не определяет его lifecycle. Tool может быть выполнен только Executor через
Registry; Planner не вызывает implementation напрямую.

Stage 4 отделил планирование от исполнения через `PlannerAdapter`. Deterministic
planner, LLM planner, replay/test planner и будущие Fast/Deep planners должны были
возвращать единый `PlannerTurn` с `ActionProposal`. Именно трактовка FAST/DEEP как
вариантов Planner позднее признана неверной границей ответственности. Остальные
проверенные свойства Stage 4 — Tool/Executor/Observation/Verification/recovery —
остаются полезным исполнительным фундаментом и не отменяются ADR-009.

Agent использует пошаговый ReAct-подобный цикл `Goal → Context → Planner proposals →
validation/Candidates → Choice → Action → ExecutionReceipt → Observation → Goal
verification`. Этот цикл остаётся реализованным и покрытым тестами, но больше не
считается каноническим главным cognitive/runtime loop ANIMA.

Operational execution history и долговременная Memory разделены. Persistent
`agent.db` хранит run/step state, proposals/selection, receipts/observations,
verification и operation IDs для restart/interruption/idempotency. Значимые факты
поведения публикуются как `agent.*` Events и могут проходить обычный Memory pipeline.

Stage 4 дошёл до 4.12 LLM Planner Experiment. 4.13–4.15 остановлены после
архитектурного аудита. Реализованные результаты и Validation Reports сохраняются как
история эксперимента и источник кода для будущей Cognitive Integration.

## ADR-009

**Accepted.** 2026-10-29, возврат к исходной когнитивной архитектуре и Stage 5 FAST.

Причина: аудит ранних концептуальных документов показал, что исходная ANIMA не
предполагала LLM главным циклом или Planner. Постоянно существуют системные сервисы
событий, памяти, задач, рабочего контекста, проверки и исполнения; Fast/Deep —
сменяемые когнитивные механизмы, вызываемые для осмысления ситуации. Stage 4
сместил эту границу, сделав LLM генератором структурированных Planner/Tool proposals.
Эксперименты с Qwen подтвердили, что существенная часть model budget тратится на
служебный contract, а не на смысловую обработку.

Stage 5 возвращает исходное разделение ответственности. FAST — первый реальный
cognitive consumer ANIMA. Он получает текущий текстовый input и ограниченный
релевантный `ContextBundle` через ANIMA Cognitive Interface (ACI) и возвращает
когнитивный результат: ответ, смысловую интерпретацию/предложение для памяти либо
запрос дополнительного контекста. FAST не является владельцем EventLog, Memory,
Knowledge, Identity, Goals, Internal State, Sleep или executor state.

Cognitive Memory остаётся независимым системным владельцем опыта. Запись проходит
через существующий Event/Memory processing path; чтение — через Retrieval и
ContextBuilder. FAST не получает прямого SQL/file write к памяти. Его интерпретация
может стать входом для системного memory processor/adapter только с сохранением
source Event и provenance. Модель не может сама повысить собственный вывод до
подтверждённого Knowledge.

Первый Stage 5 baseline намеренно текстовый: `conversation.user` Events, существующая
Cognitive Memory, bounded context и одна локальная FAST LLM через сменяемый backend.
Internal State, Sleep, DEEP, Tools, AgentLoop и физическая периферия остаются
реализованными или запланированными подсистемами, но не участвуют в baseline. Это
позволяет проверить границу cognition↔memory без смешивания нескольких механизмов.

Первый основной критерий — cross-session recall без model chat history: информация
сохраняется ANIMA в одной сессии, модель/сеанс полностью меняется или перезапускается,
после чего новый запрос получает релевантный опыт только через
`memory.db → Retrieval → ContextBuilder → ACI → FAST`. Ответ и использованные
источники должны быть наблюдаемы и прослеживаемы до raw Event.

После read path FAST может участвовать в формировании памяти как semantic interpreter,
но не как storage authority. Новый текст может породить memory candidate, изменение
или противоречие; системный слой сохраняет историю и provenance и решает lifecycle.
Замена FAST-модели не должна требовать миграции личности или стирать накопленный
опыт.

Stage 4 код не удаляется: Tool contracts, Executor, Observation, Verification,
recovery и operational storage могут быть повторно подключены на последующем этапе
Cognitive Integration. Не переносится только архитектурное предположение, что
FAST/DEEP должны реализовывать `PlannerAdapter` и что Goal-driven AgentRun является
главным циклом ANIMA.

Цена решения — временно отложенная интеграция уже готовых Internal State/Sleep/Agent
подсистем и необходимость нового ACI/FAST contract. Польза — возвращение LLM к роли,
для которой она нужна: адаптивное reasoning над изменяющимися внутренними, внешними
и смысловыми данными, тогда как рутинные операции остаются детерминированными
сервисами ANIMA. Порядок реализации — [Stage 5](../ROADMAP/README.md#stage-5).
