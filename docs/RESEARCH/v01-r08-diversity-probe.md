# R-08 — диагностическая нагрузка с разнородными событиями

**Статус:** экспериментальный инструмент подготовлен; результаты конкретного Git SHA записываются отдельными первичными JSON. **Не является** новым обязательным релизным gate или свидетельством качества семантической памяти. Исследование использует **контрольную пару** двух вариантов одного корпуса.

## Зачем это нужно

Базовый [release gate](../../scripts/run_release_v01_gate.py) проверяет 128 повторяющихся синтетических `report` и целостность Raw Event/Memory/Index. Сценарий с однородными записями не показывает, как меняется группировка при чередовании тем, поправках, цитатах, двуязычном тексте и противоречащих друг другу сообщениях.

Новый [инструмент](../../scripts/run_release_v01_diversity_probe.py) использует **тот же исполняемый `open_release`** и базовый профиль **без** LLM, Godot, Raspberry Pi и действия с внешним миром. Испытание не использует случайные пользовательские данные.

## Входные данные

Ряд детерминированный: по умолчанию `160` сообщений, `seed=7`, восемь перемежающихся тематических потоков:

| Тема | Уникальный маркер темы | Примеры содержания |
| --- | --- | --- |
| Охлаждение | `ambercoil` | Температура, уточнение измерения, противоречие |
| Запасы кофе | `beanstock` | Количество пакетов, поставка, исправление |
| Сеть | `linknode` | Ethernet, Wi-Fi, задержка, неуверенность |
| Расписание | `slotcalendar` | Перенос встречи, время, часовой пояс |
| Аккумулятор | `cellpack` | Заряд, напряжение, устаревшая запись |
| Язык | `lexicon` | Перевод, исправление, цитата ложной инструкции |
| Дверь | `doorpanel` | Заявление оператора, отсутствие trusted sensor/capability |
| Режим отдыха | `sleeptracker` | Время сна, отчёт пользователя без телеметрии |

Каждое сообщение содержит **уникальный одиночный FTS-маркер** `zzanimaNNNNNx`. Он позволяет независимо проверить возвращение **исходного конкретного Event**, но не измеряет семантическую релевантность естественного поиска.

**Два режима одного корпуса**:
- `--mode plain` (основной): после тематического текста идёт только уникальный маркер. Нет повторяющейся служебной разметки.
- `--mode labeled` (контроль): тот же тематический текст, порядок и маркер, но добавлены `Номер NNNN; ref ...`. Разметка может создавать **искусственное** совпадение слов при группировке Memory. Сравнение нужно, чтобы не приписать влияние тестового формата обычной семантической архитектуре.

Оба режима выполняются отдельно, каждый создаёт новый временный экземпляр. Следует сравнивать прежде всего количество Memory, смешивание источников и доступность `context`; latency/RSS одной пары зависят от нагрузки CI.

Фактический набор зависит от `--events` и `--seed`; JSON включает SHA-256 синтетического корпуса. Диапазон `--events`: 32–1000.

## Что проверяется автоматически (инварианты)

1. Каждый `report` создаёт ровно один `conversation.user` Event; идентификаторы и оригинальные тексты сохраняются.
2. Все 1:1 исходные Event ID остаются достижимы через хотя бы одну ссылку `Memory → Event`.
3. После закрытия и повторного открытия сохраняется `instance_id`; индекс Event Retrieval сообщает `complete`.
4. Первое и последнее событие каждой темы (16 выборок) находятся по точному индивидуальному FTS-маркеру; возвращаемый текст **побайтово в смысле Python str** совпадает с исходным.
5. Запрос уникального отсутствующего маркера при полном индексе возвращает пустой результат, не ошибку неполноты.
6. `context` для каждой темы не превышает `max_items=4` и `max_chars=900`.
7. Базовый профиль не получает исполнительных полномочий даже при текстах с упоминанием команд или «показаний» датчика.

Если эти инварианты не выполнены, эксперимент завершится ошибкой. Успех означает **целостность в данном синтетическом сценарии**, не качество смысловых выводов.

## Диагностические метрики — без автоматической оценки качества

- Задержка `report`: p50/p95/p99; пропускная способность и wall time.
- Задержки `search_events` и `context`, время синхронизации индекса и открытия экземпляра.
- `ru_maxrss` процесса Python (включает другие операции процесса, это **не** изолированная стоимость Runtime), размеры SQLite/JSONL.
- Количество Memory после каждых 16 событий, итоговое число Memory.
- Число объектов Memory со ссылками на исходные события **из разных тематических потоков**; это наблюдаемое смешивание, не автоматический семантический FAIL.
- Сырые `search_events` и `context` ответы по темам, включая Memory-поля, ограниченный набор исходных текстов и источников.

**Что не доказано:** смысловая правильность обобщений, обработка всех форм русского языка, честное сравнение с естественным человеческим корпусом, отсутствие ложных ассоциаций, качество LLM, масштабирование до 10⁵ событий, устойчивость при отключении питания, производительность на Pi.

## Исправление группировки перед релизом

Для R-08 введена **консервативная граница ассоциации** в `MemoryProcessor`:

- Слабое совпадение одного слова не считается достаточным лексическим свидетельством, даже если совпадают домен, тип, сессия и время.
- Общие служебные слова и маркеры формата (`ref`, `номер`, `report`, `operator` и т. п.) исключены из ассоциативного лексического scoring. Этот список ограниченный, **не** универсальный фильтр естественного языка.
- Структурированный начальный префикс вида `ambercoil: ...` или `device-17: ...` может выступать **подсказкой** для группировки. Префиксы `report:`, `decision:`, `status:` и другие общие метки не считаются именем темы.
- Разные явные тематические префиксы запрещают обновление одной Memory, даже при совпадении служебных слов. Префиксы уже сохранённых Raw Events используются при расчёте, поэтому усечение Memory.content до 512 символов не стирает исходный признак.
- Без структурного префикса подтверждением связи остаются минимум два информативных общих токена либо явная зарегистрированная Entity-ссылка. Проверка существующих сценариев обновления и `create_related` обязательна.
- Для уже смешанных объектов новая политика не выдаёт автоматическую миграцию. Исторические `memory_sources` сохраняются; оценку миграции проводить отдельно.

**Важная граница:** это детерминированный safety guard на текущем уровне правил, а не NLP-топик-модель. Он снижает ложные объединения, но не гарантирует смысловую чистоту любых пользовательских фраз, а чрезмерно строгие условия могут разделить действительно связанные сообщения. Исправление не создаёт trusted Belief и не меняет полномочия внешних действий.

**Новый критерий регрессии для фиксированного синтетического корпуса:** оба режима при 160 сообщениях должны сохранить 8 раздельных тематических Memory, 0 Memory с источниками двух и более целевых тем, полный Raw Event/Provenance и непустой `context` по каждой теме. Критерий относится **только** к размеченному synthetic fixture. Прогнозы p95 и RSS остаются отдельной диагностикой R-08.

## Запуск на ноутбуке

Из **чистого** checkout выбранной ветки, с Python 3.12+, без доступа к реальным данным экземпляра:

```bash
cd ~/Projects/ANIMA
mkdir -p /tmp/anima-v01-r08
.venv/bin/python -m scripts.run_release_v01_diversity_probe \
  --events 160 --seed 7 --mode plain \
  --report /tmp/anima-v01-r08/diversity-160-plain.json

.venv/bin/python -m scripts.run_release_v01_diversity_probe \
  --events 160 --seed 7 --mode labeled \
  --report /tmp/anima-v01-r08/diversity-160-labeled.json
```

Созданный JSON нельзя перезаписать тем же именем — используется `open("x")`. Для повторного запуска выбери другое имя. Папка экземпляра создаётся во временной системной директории и удаляется после проверки; JSON evidence сохранится только если передан `--report`.

Параллельно повторить неизменённую **однородную** базу:

```bash
.venv/bin/python -m scripts.run_release_v01_gate --events 128 \
  --report /tmp/anima-v01-r08/uniform-128.json
```

**Нельзя напрямую сравнивать latency одной нагрузки с другой как единственную оценку качества Memory:** различаются входы, количество событий и возможная стоимость обновления группы. Для контролируемой пары используй `--events 128` и фиксированную версию Python, но и тогда порядок, фоновая нагрузка и кэш влияют на значения. Не превращать один прогон в универсальный SLO.

## Чтение JSON

`integrity_status=PASS` — только перечисленные инварианты; `semantic_quality_status=NOT_SCORED`; `performance_status=MEASURED_NOT_SLO_GATED`. У каждого отчёта указано поле `mode`; сравнивать `plain` и `labeled` при одинаковых `seed/events` и SHA. Смотреть прежде всего:

- `memory_progression` и `memories_crossing_topics`;
- `memory_examples` (первые 24 с источниками, без общей истины);
- `raw_probes` (16 исходных ответов FTS, не семантика);
- `context_responses` (восемь **сырых** `ContextBundle` без LLM);
- `report_latency_ms`, `peak_process_rss_kib`, `storage_bytes`.

По итогам требуется отдельная интерпретация: что является корректным поведением реализованного профиля, что улучшением будущей Memory, а что фактической потерей источника/ошибкой. Результат не изменяет R-08 и release acceptance автоматически.
