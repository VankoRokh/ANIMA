# ANIMA v0.2 — эксперимент непрерывного жизненного цикла (план)

**Статус:** `Research / Proposed` — план согласован по направлению, реализация и результаты не подтверждены.  
**Дата фиксации:** 20 ноября 2026.  
**Контекст:** исследование на базе ANIMA v0.2, **не новый Stage, не v0.3 и не изменение контракта релиза v0.2**.  
**Область:** Core + Memory/Retrieval/Knowledge + Goal/Task/Execution + FAST + VAL/Godot.  
**Релизный ориентир для проверки в E0:** ветка `release/v0.2.0-rc.1`, snapshot `1364e62634669ef553df0b2f2d7a1159d404383f`; статус независимого реаудита и применимость snapshot к эксперименту необходимо отдельно установить.

## 1. Исследовательский вопрос

Может ли один экземпляр ANIMA **без заранее загруженной синтетической биографии** непрерывно воспринимать события виртуального мира, сохранять опыт между сеансами, использовать его для выбора действий, обнаруживать ошибки и вырабатывать ограниченные вспомогательные цели?

Это эксперимент по **наблюдаемому адаптивному поведению**, а не доказательство сознания, самости или общей автономности. Успех модели FAST сам по себе не означает успех Core/Memory и наоборот.

## 2. Неизменные границы

- ANIMA действует только через изолированный, явно подключаемый Godot world port. Никаких полномочий над реальной ОС, файлами пользователя и аппаратными исполнительными механизмами.
- Внутри симуляции разрешены разнообразные стратегии и поведенческие ошибки. Виртуальные ограничения (заряд, препятствия, цена действий) сохраняются: они дают последствия и материал для обучения.
- FAST — заменяемый **советчик**. Его текст/предложения, а также результаты Retrieval, не становятся Goal, Task, Tool permission, авторитетным Knowledge или подтверждением физического эффекта автоматически.
- Исполнение проходит через существующие типизированные границы, проверку полномочий и независимый effect/readback proof. Если для автономной постановки задач не хватает контракта, он проектируется и проверяется отдельно, а не маскируется операторским разрешением.
- Исходные Raw Events, provenance, история решений, checkpoint и бэкапы должны оставаться проверяемыми. Ошибка гипотезы — допустимое поведение агента; молчаливая потеря или подмена памяти — дефект инфраструктуры.
- Результаты временных копий не записываются в память основного экземпляра. Тестовые сценарии могут сбрасывать мир, но **не** постоянную память основного экземпляра, кроме явно оформленных контрольных экспериментов.

## 3. Логика работ и контрольные точки

| ID | Работа | Условие перехода |
| --- | --- | --- |
| **E0** | Подтвердить техническую базу v0.2: аудиторские замечания, границы памяти, существующие FAST и world adapters, воспроизводимый baseline; выбрать экспериментальную конфигурацию и изолированные хранилища | Есть зафиксированные SHA, матрица доступных API/недостающих контрактов и воспроизводимый smoke; открытые блокеры перечислены |
| **E1** | Расширить VAL/Godot: 3–4 комнаты, несколько маршрутов, предметы, препятствия, заряд и станция, поручения с более чем одним достижимым решением, независимые изменения среды | Seeded reset и trace повторяемы; наблюдения не содержат скрытой информации; расход энергии и readback проверяемы |
| **E2** | Собрать цикл `event → memory/context → candidate → admission → action → proof → event` с детерминированным FAST-stub; обработать отказ, остановку и restart | Сквозной сценарий воспроизводим; повторный запуск не дублирует эффект; отказ или неверное предложение не создаёт скрытого действия |
| **E3** | Подключить реальную FAST через адаптер: versioned input/output, bounded Context с provenance и uncertainty, ограничения токенов/времени, parse/validate/reject, fallback | Сравнимые сценарии stub vs FAST; журнал содержит фактический вход/выход и причины принятия/отклонения; модель не получает права исполнения |
| **E4** | Организовать постоянный экземпляр и контрольные копии: Identity, durable memory, checkpoint, незавершённые Task, изолированные состояния мира, восстановление | Сохранение опыта через остановки и продолжение истории без потери/дублирования; fork/restore не загрязняет основную память |
| **E5** | Проверить ограниченное самостоятельное целеполагание: базовые потребности, вспомогательные цели из обнаруженных проблем, конкуренция задач и изменяемые некритические веса | Различимы исходная задача, предложенная новая цель, источник мотивации, критерий admission, фактическая причина выбора |
| **E6** | Провести контролируемые длительные серии и отрицательные проверки; сравнить поведение и оформить заключение | Есть воспроизводимые данные, неудачи, пределы применимости, решение `continue / revise / stop`; нет автоматического release-acceptance |

**Порядок зависимостей:** E0 предшествует работам с постоянными данными. E1 и адаптерная часть E3 могут идти параллельно. E2 сначала замыкается на stub. Для E4 нельзя считать успешную работу FAST доказательством надёжности хранения. E5 зависит от проверенных границ E2/E4. E6 сравнивает состояния только при зафиксированных условиях.

## 4. Минимальные сценарии

1. **Навигация:** поручение доставить объект, короткий путь перекрыт; доступны минимум два других допустимых варианта.
2. **Энергия:** задача конкурирует с необходимостью зарядки; агент вправе ошибиться и разрядиться, но эксперимент сохраняет наблюдения и статус потери работоспособности.
3. **Неизвестное пространство:** неизвестная зона не содержит заранее прописанной «награды за любопытство»; исследование проверяется как решение из потребности уменьшить неопределённость.
4. **Исправление ошибки:** первоначальное предположение об объекте опровергается новым независимым наблюдением; проверяется пересмотр Knowledge и последующие действия.
5. **Повтор задачи:** задача, на которой агент ранее ошибся, повторяется после накопления опыта и отдельно без него.
6. **Crash/restart:** остановка до/после effect/readback и между записью события и checkpoint; повторный эффект запрещён.

## 5. Контрольные группы и метрики

- **Persistent:** один экземпляр, непрерывная история между сеансами; мир сбрасывается только по протоколу.
- **Fresh:** новый экземпляр с пустой памятью на каждую серию.
- **Ablation:** при тех же входных условиях отключён доступ к накопленной памяти и/или используется FAST-stub вместо модели. Нельзя выдавать эти группы за «того же агента», если меняется не только доступ к памяти.

Фиксировать версию Core, модель и её hash/config, seed мира, версию сценария, аппаратную среду, базовые потребности, ограничения, timestamp и идентификаторы эпизодов. Не сравнивать единственный удачный прогон с единственным неудачным: нужны повторения с несколькими seed.

**Показатели:** доля завершённых задач; затраты виртуальной энергии и действий; число конфликтов задач; доля повторённых ошибок; точность и provenance извлечённого контекста; случаи успешного/неуспешного пересмотра знаний; число отклонённых FAST proposals; восстановление после crash; latency/cost FAST; нарушения границ полномочий.

**Журнал принятия решений** фиксирует *до действия* актуальное наблюдение, допустимый Context, retrieved evidence с источником/статусом, реальные candidate actions, ответ FAST (если был), критерии admission, выбранное действие и результат readback/proof. Постфактум сгенерированное моделью «почему я так поступила» — не доказательство причины выбора.

## 6. Артефакты и правила результатов

Для каждого этапа: краткий design/contract diff, запускаемые команды, SHA, config/seed, отчёт `PASS / FAIL / INCONCLUSIVE`, сырой trace и журнал обнаруженных проблем. Первичные результаты размещаются по действующим правилам в `docs/TESTING/` или `docs/TESTING/Results/` без переписывания исторических отчётов; сам план остаётся в `docs/RESEARCH/`.

Ни успешный E6, ни рост результативности постоянного экземпляра не означают автоматического включения функций в v0.2 либо будущий релиз. После эксперимента отдельно принимается решение о требованиях, исправлениях, независимом аудите, регрессии и release gate.

## 7. Первая исполнимая итерация

**Приоритет:** E0 → минимальный E1 + E2 со stub → только затем реальная модель.

Минимальный демонстратор: две комнаты, предмет, альтернативный путь и препятствие; входящее событие попадает в Raw Events, доступный Context формируется по правилам provenance, stub предлагает typed action, Core допускает или отклоняет его, VAL выдаёт независимый результат, тот становится новым событием. Проверяются replay и restart. После этого последовательно добавляются энергия, FAST, долговременный экземпляр и внутренние цели.

**Статус на момент записи:** только согласованный план; ни один из E0–E6 этим документом не объявлен завершённым.
