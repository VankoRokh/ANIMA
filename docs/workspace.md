# Рабочее пространство ANIMA

**Назначение:** поддерживать чистую локальную среду разработки, не смешивая Git-исходники, инструменты инференса, модели и данные экземпляров. Эти правила относятся к **рабочему компьютеру**, а не к контракту ANIMA v0.1. Запуск и восстановление самого экземпляра описаны в [эксплуатации](operations.md).

## Рекомендуемая структура

```text
~/Projects/
├── ANIMA/            # единственный постоянный рабочий checkout
├── models/           # общие GGUF, не входят в Git ANIMA
└── llama.cpp/        # самостоятельный Git checkout и локальная сборка
```

Внутри `ANIMA/`: `anima/` — код, `config/` — версионируемые профили и локальный необязательный конфиг, `docs/` — документация, `labs/` — лаборатории, `scripts/` — инструменты, `tests/` — проверки. Устройство пакета `anima/` не зависит от названия внешнего каталога `~/Projects/ANIMA`.

| Данные | Хранение | Git |
| --- | --- | --- |
| Код, схемы, fixtures и документация | `ANIMA/` | Да, по правилам проекта |
| Модели `*.gguf` | `models/` | Нет |
| Сборка `llama-server` | `llama.cpp/build/` | Не в Git ANIMA |
| `.venv`, `.venv-qwen-agent`, `__pycache__` | Локально в рабочей среде | Нет |
| `.benchmarks/`, временные логи и кеши | Локально; ценные evidence переносить отдельно | Нет |
| Данные реального экземпляра, SQLite, `events.jsonl` | В **отдельном** каталоге, явно указанном через `--data-dir` | Нет |
| Резервные копии данных | Отдельно от checkout, с независимой копией | Нет |
| `.obsidian/` | Настройки одного выбранного Obsidian vault | Нет |

**Никогда** не переносить каталог работающего экземпляра или SQLite-файлы как «папку проекта». Сначала корректно остановить процесс, затем делать согласованную копию согласно [operations.md](operations.md). Не смешивать данные старого CLI (`ANIMA_DATA_DIR`) и нового `release_v01 --data-dir`.

## Единая конфигурация внешних путей

Восемь opt-in скриптов Stage 5 / FAST-DEEP / Stage 6 читают пути через [`scripts/workspace_paths.py`](../scripts/workspace_paths.py). Это **не** runtime Core и не конфигурация полномочий LLM.

Стандартные пути остаются прежними: `~/Projects/models` и `~/Projects/llama.cpp/build/bin/llama-server`. Для сохранения текущей установки ничего создавать не требуется.

Если нужно переопределить расположение, создать **только локально**:

```bash
cp config/workspace.example.json config/workspace.local.json
```

Пример `config/workspace.local.json`:

```json
{
  "projects_root": "~/Projects",
  "models_root": "~/Projects/models",
  "llama_server": "~/Projects/llama.cpp/build/bin/llama-server"
}
```

`projects_root` задаёт корень, от которого по умолчанию вычисляются `models_root` и `llama_server`. Два последних ключа необязательны и могут независимо менять пути. Использовать абсолютные пути или `~/...`, не относительные пути от текущей директории. Файл `config/workspace.local.json` исключён из Git; [образец](../config/workspace.example.json) версионируется.

Для временного переопределения без редактирования файла:

```bash
export ANIMA_PROJECTS_DIR="$HOME/Projects"
export ANIMA_MODELS_DIR="$HOME/Projects/models"
export ANIMA_LLAMA_SERVER="$HOME/Projects/llama.cpp/build/bin/llama-server"
```

Порядок приоритета для каждого пути: **аргумент командной строки → профильная переменная окружения → локальный JSON → корневой каталог → стандартное значение**. CLI-параметры `--models-root`, `--server-binary`, `--model-file`, `--binary`, `--model` сохранены.

**Пример проверки без запуска модели:**

```bash
python3 -c 'from scripts.workspace_paths import models_root, llama_server_binary; print(models_root()); print(llama_server_binary())'
python3 -m pytest -q tests/test_workspace_paths.py
```

Отсутствующая модель или исполняемый файл — ошибка при запуске соответствующего эксперимента, а не повод автоматически скачивать файлы. Изменение пути не меняет checksums, модельные benchmark evidence, acceptance v0.1 и source authority.

## Правила Git и worktree

1. **Один постоянный checkout:** `~/Projects/ANIMA`. Краткосрочные эксперименты — отдельные ветки или временные worktree `ANIMA-<тема>`. После эксперимента не оставлять каталог «на всякий случай».
2. **Перед созданием worktree:** записать исходный SHA, имя ветки, назначение, критерий завершения. Не использовать одно имя каталога для разных checkout.
3. **Перед удалением:** проверить `git worktree list`, `git status --porcelain=v1 --untracked-files=all`, `git clean -ndx`, наличие коммитов в удалённой истории и ценных игнорируемых evidence. `git clean -ndx` — только предварительный просмотр, а не приказ удалять.
4. **Удалять штатно:** `git worktree remove <путь>` после проверки/очистки ненужных ignored-файлов. Не использовать `rm -rf`, `--force`, `git reset --hard` для «наведения порядка».
5. **Ветки отдельно от каталогов:** локальную ветку удалить через `git branch -d` лишь после проверки, что нужные коммиты доступны в remote или архиве. **Не удалять remote-ветки автоматически.**
6. **Каждая работа имеет границы:** новый функционал — отдельная ветка/PR и тесты; экспериментальные результаты фиксируются с SHA; не смешивать перестройку файлов, изменение Core и release acceptance в один commit.
7. **Обновление:** `git fetch origin`, затем `git status --short --branch`; применять `git pull --ff-only` только там, где это действительно fast-forward. Не переключать живой экземпляр на новую схему без миграционного плана.
8. **Периодическая ревизия:** после завершения вехи удалять завершённые временные worktree, просматривать `.benchmarks`, данные и размер моделей; сохранять репрезентативные первичные доказательства до удаления кешей.

## Obsidian

Для документации ANIMA можно открыть **`~/Projects/ANIMA` как отдельный vault**. Локальные настройки будут в `ANIMA/.obsidian/` и не должны попадать в Git. Существующий `~/Projects/.obsidian/` является *другим vault*: не удалять его и не переносить настройки автоматически, пока не проверены нужные плагины и рабочее пространство.

Не создавать отдельную долговременную копию Git-документации ради Obsidian. Достаточно читать Markdown в рабочем checkout; изменения документации проходят обычный Git review и [редакционные проверки](documentation.md).

## Проверка чистоты

```bash
cd ~/Projects/ANIMA
git status --short --branch
git worktree list
bash scripts/check.sh
python3 -m pytest -q tests/test_workspace_paths.py
```

Отсутствие модификаций в `git status` **не** означает отсутствие игнорируемых файлов. Модели, приватный JSON, данные и бэкапы не должны становиться частью PR или артефактов CI.
