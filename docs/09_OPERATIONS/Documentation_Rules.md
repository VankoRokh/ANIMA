# Правила документации

## Главный принцип

**Один факт — одно каноническое место.** Другие страницы могут ссылаться на него, но не должны вручную поддерживать собственную копию того же статуса, списка задач или результата теста.

Документация хранится вместе с кодом в `docs/`. Git хранит историю изменений; поэтому живые страницы не должны выполнять роль ручного changelog.

## Канонические источники

| Вопрос | Каноническое место |
|---|---|
| Что происходит сейчас? | `00_HOME/Project_Status.md` |
| Что такое ANIMA и зачем она создаётся? | `00_HOME/ANIMA.md`, `01_CONCEPT/` |
| Как система должна быть устроена? | `02_ARCHITECTURE/`, `05_PROTOCOLS/` |
| Что реально реализовано в коде? | код + описание соответствующего software/module раздела |
| В каком порядке развиваем проект? | `06_ROADMAP/Roadmap.md` и страница Stage |
| Почему принято важное решение? | `08_DECISIONS/` |
| Как проверяем систему? | `07_EXPERIMENTS/Test_Strategy.md` |
| Какие проверки стоит сохранить? | `07_EXPERIMENTS/Test_Results.md` |
| Как работать, запускать и восстанавливать? | `09_OPERATIONS/` |

## Что обновлять после изменения

Не существует обязательного правила «обновить пять страниц после каждого commit».

Обновляется только то, что действительно изменилось:

- изменилось текущее положение проекта → `Project_Status.md`;
- изменился контракт/архитектура → соответствующий архитектурный документ;
- изменился порядок или критерий этапа → Roadmap/Stage;
- принято важное решение с последствиями → ADR;
- получен показательный результат → `Test_Results.md`;
- обычный успешный локальный test/check → документацию не менять.

## Статусы

| Объект | Статусы |
|---|---|
| Решение модуля | Accepted / Draft / Experiment |
| Реализация | Planned / Prototype / Implemented / Tested / Stable / Deprecated |
| Stage | Planned / InProgress / Complete / Blocked |
| Experiment | Planned / Active / Successful / Failed / Inconclusive |
| ADR | Draft / Accepted / Superseded / Rejected |

`Tested` требует конкретной проверки. `Stable` требует повторяемой работы в реальных условиях и известных ограничений.

## Stage

Страница этапа должна отвечать на шесть вопросов:

1. Какое свойство системы мы хотим получить?
2. Что должно быть готово до старта?
3. Какие задачи необходимы для достижения цели?
4. Что можно наблюдать или измерить после реализации?
5. Какими сценариями мы проверяем результат?
6. Какое условие закрывает этап?

После завершения Stage подробные доказательства хранятся в результатах тестирования, а не копируются в статус проекта.

## Ссылки

Ссылки добавляются для навигации по необходимости. Не требуется связывать каждую страницу со всеми родственными страницами. Предпочтительны ссылки на канонический источник, а не цепочки из нескольких промежуточных документов.

## AI и возвращение после перерыва

Человеку достаточно начать с `START_HERE.md`. ИИ-помощнику — с `AI_CONTEXT.md`. Оба маршрута должны быстро приводить к одному `Project_Status.md`, Roadmap и нужному модулю.

## Проверка

`bash scripts/check.sh` остаётся быстрой проверкой целостности проекта. Он не заменяет feature tests, stage validation и эксперименты.

При расширении автоматизации проверять только то, что реально помогает находить ошибки. Метрика «количество ссылок/страниц» сама по себе не является целью качества документации.
