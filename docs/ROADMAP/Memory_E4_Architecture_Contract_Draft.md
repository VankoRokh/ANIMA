# ANIMA — E4 Unified Architecture Contract (draft)

**Статус:** согласованная концепция / проект архитектурного контракта; **не** production implementation и **не** ратифицированный ADR.  
**Дата:** 2026-11-12.  
**Рабочая ветка:** `experiment/core-memory-information-baseline`.  
**Связанные документы:** [Memory Architecture Roadmap](Memory_Architecture_v1_Roadmap.md), [Memory Encoding E1](Memory_Encoding_E1_Results.md), [E2](Memory_Encoding_E2_Brief.md), [E3](Memory_Encoding_E3_Review_Brief.md), [Stage 7 Semantic Boundary](Stage_7_Semantic_Boundary_v0.md).

> Решения ниже согласованы на концептуальном уровне. Точные схемы, контракты времени, policy-границы и миграции требуют отдельных design/negative gates. Функциональные E2/E3 и E1 compression adversary не становятся PASS от принятия этого документа.

## 1. Цель

Создать устойчивое к компрессии представление опыта, в котором ANIMA может:

1. Разделять первичные Events, ограниченные Episodes и связывающие несколько эпизодов Stories;
2. Обнаруживать неопределённость как самостоятельную информацию, а не ошибку;
3. По решению Core создавать исследовательские Goal/Task, выполнять их длительно, ставить в очередь, ожидать условий и **периодически возвращаться к важному вопросу**, даже без новых Events;
4. Пользоваться накопленными проверенными соответствиями между именами и Entity, не вызывая дорогой анализ повторно;
5. Восстанавливать работу после interruption/crash и пересматривать derived-структуры, не переписывая первичную историю и не повышая достоверность без полномочий.

## 2. Разделение владения и представлений

| Слой | Владелец/назначение | Непременная граница |
| --- | --- | --- |
| `Event` | Authoritative запись сообщения/наблюдения в принадлежащем источнику store | Raw ≠ истина содержания, duplicate projections ≠ independent evidence |
| `Episode` | Версионированная организационная проекция ограниченного набора первичных Event IDs | Не заменяет raw Events и не задаёт authority |
| `Story` | Производная версия связи нескольких Episodes в продолжающуюся историю | Story не обязана физически сливать или переписывать Episodes; пересматриваема |
| `Entity Resolution` | Механизм идентификации и контекстных алиасов, отдельный от MemoryProcessor | Alias/LLM-предположение не подтверждает физическую идентичность без оснований |
| `Uncertainty Registry` | Хранит вопрос, provenance, неизвестное/противоречие/недостаток метода и версии | Не создаёт Goals/Tasks или Knowledge автоматически |
| `Core Goal/Task` | Решение об исследовании, допуске методов, бюджете и исполнении | Только Core владеет постановкой и переходами Goals/Tasks |
| `Investigation Policy/Schedule` | Предложение и durable-план следующей допустимой попытки | Состояние расписания не подменяет состояние Goal/Task и результат знания |
| `FAST/DEEP/SLEEP` | Режимы доступной вычислительной обработки | Сменные потребители, не владельцы памяти/истины |

## 3. Episode vs Story

`Event → Episode → Story` — уровни организации, а не три независимые первичные записи.

**Episode:** ограниченный фрагмент конкретного протекания/взаимодействия, с source Event IDs, временной областью, Entity refs, причиной границы, версией группировки и полнотой охвата.

**Story:** объединение эпизодов, предположительно относящихся к одной продолжающейся ситуации, например обнаружение перегрева → диагностика → ремонт → проверка. Story имеет собственную версию, источники связи, тип/статус отношений и признак неопределённости; не переводит содержание эпизодов в подтверждённое Knowledge.

**Границы:** время/сессия/Entity/context — разные признаки. Смена сессии обычно склоняет к новому Episode, но не запрещает Story continuity. Доказанно разные объекты могут запрещать merge конкретного единичного случая, но не запрещают общий контекст нескольких устройств. Фактор оценки не превращать в универсальный запрет.

**Association policy:** сначала проверка противопоказаний (identity/scope/provenance), затем дешёвое детерминированное сопоставление, затем допустимые кандидаты, затем DEEP/другой метод только при оправданной ценности. `create_related` ≠ `same_episode`.

## 4. Entity Resolution, обучение и границы истины

Называть два слова синонимами недостаточно. Хранить отдельное **контекстное соответствие** (`surface_form`, `entity_id`, `scope`, `source_event_refs`, `method`, `status`, `version`, `reconsider_when`).

Предположение «адаптер» и «блок питания» обозначают одну Entity не устанавливает это без проверки. Ответ пользователя может подтвердить **подразумеваемый референт конкретного сообщения**, но не автоматически реальные электротехнические свойства объекта или истинность других Claims.

Путь: быстрый известный alias → дешёвая локальная Entity/Memory retrieval → структурный контекст → при необходимости ограниченная LLM/DEEP-интерпретация, внешний источник, уточнение пользователя. **Это предпочтительная последовательность затрат, не жёсткий порядок**: если пользователь — единственный авторитетный источник личного значения и контакт уместен, запрос может быть дешевле DEEP.

Зафиксированная ошибочная идентичность должна порождать **bounded пересмотр зависимых derived Episode/Story links**, а не уничтожение исходных Events. Ошибка и основание исправления — часть опыта; повторный запуск того же метода на неизменных данных не считается обучением. Самоизменение production-правил без отдельного gate запрещено.

## 5. Три независимые оси долгого исследования

**A. Эпистемический статус вопроса** (концепт; не использовать как существующие значения Core enum):

`unresolved`, `resolved_in_scope`, `closed_unresolved`. Вопрос может снова открываться при версии новых оснований. Дополнительно хранить причину недостаточности и точную область проверенного ответа.

**B. Состояние исполнения** — канонический Goal/Task lifecycle, который уже существует:

- В `anima/internal_state/goals.py`: Goal `active | blocked | completed | cancelled`.
- В `anima/tasks/contracts.py`: Task `queued | active | interrupted | completed | failed | cancelled`.

Не добавлять несуществующие `waiting_condition` или `scheduled` в эти enum только ради E4. Многочасовое исследование может состоять из нескольких Tasks под одним Goal; между попытками Core может оставлять Goal `blocked`, а следующую Task ещё не создавать. Завершение попытки Task ≠ разрешение вопроса; `Task.failed` ≠ `Uncertainty.closed_unresolved`.

**C. Допуск к следующему запуску** — отдельная система планирования (проектируемый контракт):

- `eligible_now` — условия соблюдены и budget позволяет.
- `queued_by_core` — выбранный Core способ ждёт ресурса/приоритета, используя существующий Task `queued`.
- `wait_until(t)` — осмысленное ожидание времени, с указанной clock domain.
- `wait_for(predicate, dependency_refs)` — ожидание определённого условия/ответа/доступности метода.
- `periodic(interval_policy, next_eligible_at)` — **важное** исследование возвращается к повторной проверке, даже без внешнего Event, с новым occurrence ID.
- `suspended` — явная пауза по бюджету/политике/запросу пользователя.
- `stopped` — окончание расписания или Goal; регистрация вопроса может оставаться.

Это не новые `Task.status`: это проектируемая модель `InvestigationSchedule` / activation eligibility.

## 6. Периодические исследования — уточнение владельца

Не вводить запрет «без новых данных повтор никогда невозможен». Для значимых исследовательских вопросов периодичность сама может быть оправданным **условием активации**.

Надёжное правило двух независимых триггеров:

1. **Event-triggered:** поступили новые сведения, ответ пользователя, изменился capability или приоритет.
2. **Time-triggered:** подошло `next_eligible_at` по утверждённой для вопроса политике `periodic`.

Периодический тик вызывает **сначала дешёвую preflight-проверку** (новые данные? ранее испробованные методы? доступные ресурсы? поменялась значимость?), а не автоматически дорогой DEEP/интернет/опрос пользователя.

Если фактов не прибавилось, метод уже исчерпан или затраты превышают предел, допустимый результат: `no_progress`, обновление `next_eligible_at` и/или новое условие. Но периодический review для важного вопроса **не исчезает бессрочно** только потому, что последняя попытка была безрезультатной.

Политика допускает фиксированный интервал либо adaptive backoff до предельной частоты; конкретные интервалы и приоритетные классы **не согласованы** и должны быть проверены отдельно. Для critical blocker возможен более частый, дешёвый review. Для low-priority интереса — SLEEP/batch. Опрос пользователя имеет отдельные rate limits; периодичность пересмотра не означает повторного вопроса пользователю по таймеру.

## 7. Схема будущего InvestigationSchedule (логический контракт, не миграция)

```text
InvestigationSchedule
  uncertainty_id           # одна неопределённость, несколько попыток
  goal_id                  # nullable до допуска Core
  activation_policy        # event | condition | periodic | mixed
  next_eligible_at         # с явной clock/time-zone областью
  wake_predicates          # системные refs, не свободные исполнимые строки
  priority_snapshot        # пересчитывается Core по допустимым сигналам
  resource_budget          # CPU/time/token/network/user-interruption limits
  method_history_refs      # попытки, затраты, ошибки, причины no_progress
  checkpoint_ref           # durable прогресс долгой задачи
  last_evaluated_version   # версии данных/методов, проверенные preflight
  occurrence_key           # стабильная идентичность одного scheduled запуска
  status_reason, updated_at, version
```

`Uncertainty` существует независимо от `Goal`; один Goal может адресовать группу неопределённостей; один вопрос может пройти несколько последовательных Tasks и методов. Долгие задачи используют checkpoints и resume, а не бесконечно удерживают runnable slot.

**Идемпотентность:** scheduler должен атомарно claim-ить `occurrence_key` и фиксировать успешность/ошибку попытки; после crash один и тот же occurrence не создаёт дублирующих Effects, Goal или запросов пользователю. Разные occurrence одного периодического исследования — это разные попытки, **не независимые свидетельства**. Успех/ошибку методов нельзя выдумывать из отсутствия исполнения. Приёмка recovery должна учитывать границы разных SQLite databases и уже существующие idempotent/ledger контракты.

## 8. Самостоятельная постановка исследовательских целей

ANIMA может **предлагать** собственную исследовательскую цель по практической необходимости, совершенствованию навыков/знаний либо интересу к новому.

Core принимает решение по: значимости, риску, перспективе разрешения, текущей нагрузке и доступным ресурсам, повторяемости, сроку, доступным полномочиям, ограничению пользовательских прерываний и ожидаемому информационному эффекту.

**Постановка Goal не даёт прав на произвольное действие.** Каждый метод (локальная обработка, LLM, внешняя сеть, запрос человеку, воздействие на оборудование) отдельно проходит policy/admission и, если применимо, independent Verification. Отказ пользователя отвечать и неопределённость — допустимые результаты; они не считаются ложью, ошибкой пользователя или подтверждением альтернативного ответа.

Способ уведомления пользователя: `immediate` (существенный блокер/риск), `deferred` (контекстно уместный момент), `batch` (группа однородных вопросов). Пределы частоты и право отказа обязательны.

## 9. FAST / DEEP / SLEEP как потребители

- **FAST:** быстрые локальные алиасы, bounded retrieval, первичная ассоциация Episodes и регистрация нерешённого; не должен ждать длительный поиск.
- **DEEP:** ограниченное исследование ambiguous cases, model/tool if allowed, proposal и явные evidence gaps.
- **SLEEP:** batch review истёкших условий, пересмотр dependent links, consolidation и предложения на изменение derived views; повторный запрос того же без новых оснований не запускается автоматически только потому, что наступил SLEEP.

Длительные исследования — Goals/Tasks Core, а не удерживаемые синхронные вызовы FAST/DEEP. Режим потребления не является владельцем самих данных.

## 10. Правила остановки, ожидания и пересмотра

Допустимы результаты: `resolved_in_scope`, `insufficient_evidence`, `no_progress`, `method_unavailable`, `awaiting_user`, `budget_exhausted`, `unsafe_without_approval`, `cancelled_by_policy`.

Они **не** являются существующими Task enum и не переводятся механически в `failed` или `completed Goal`; это outcome исследования, который Core интерпретирует. Сохранять provenance, затраты, исходные версии, успешные/неудачные попытки и причину следующей активации.

Если новый факт опровергает старый alias/Story link: создать версию предложения об изменении, проверить зависимости, применить допустимую публикацию atomically/idempotently; primary raw не изменять. `review_ready` или LLM suggestion не является Knowledge `confirmed`.

## 11. E4 экспериментальные gates

| Gate | Испытание | Обязательный критерий |
| --- | --- | --- |
| E4-A | Длинные, перемежающиеся, контекстные Episodes | Отдельные случаи не сливаются; false merge/split и source IDs доступны |
| E4-B | Межсессионная / многодневная Story continuity | Story link можно предложить без merge; time/scope explicit |
| E4-C | RU/EN aliases, перефраз и ложные эквивалентности | Known alias cache используется повторно; сомнение ≠ auto-resolved |
| E4-D | Late events, исправление Entity, re-encoding | Прозрачные версии, полный provenance, replay без дублей |
| E4-U | Неопределённость → исследование → schedule | Нет автоматического Goal от любого unknown; valid conditional/periodic/queued/paused |
| E4-R | Tick без новых Events, повтор, crash/restore, user refusal | Важный question проверяется периодически без loop; один occurrence → один claim/effect |
| E4-P | Бюджеты FAST/DEEP/SLEEP и user interruption | No starvation для обычных Goals; bounded CPU/time/network/token budget |

Нужен **внешне размеченный frozen corpus** с отрицательными сценариями, равными бюджетами, raw decisions и измерениями. Семантическая корректность не выводится из зелёного CI. Прототип scheduler — отдельный design gate, а не часть E4 MemoryProcessor.

## 12. Открытые технические решения

1. Домены времени для `next_eligible_at` и логика после смены часов, перезагрузки, сна и недоступных часов.
2. Политика periodic: per-priority диапазоны, backoff/cooldown, гарантии fairness и защита от starvation; без произвольных чисел до измерений.
3. Границы источника authority для alias подтверждения и явная scope-спецификация.
4. Durable schema `UncertaintyRegistry`, `Story`, `InvestigationSchedule` и механизм versioned review.
5. Порядок замены E1/E2/E3 shadow: **после** их положительных независимых gates и E4 отрицательных сценариев.
6. Привязка к актуальным Goal/Task и Core scheduling: `GoalStore` имеет `active/blocked/completed/cancelled`, `TaskStore` — `queued/active/interrupted/completed/failed/cancelled`. Системный `CoreAutonomy` сейчас реализует ограниченный event/goal-triggered one-door профиль и **не** является универсальным periodic research scheduler.

**Решение о реализации:** документ не даёт разрешения на миграцию production stores, создание autonomous Goals или новых полномочий Core. Эти функции вводятся только через отдельную проверку контрактов, тесты recovery/authority и явный integration gate.
