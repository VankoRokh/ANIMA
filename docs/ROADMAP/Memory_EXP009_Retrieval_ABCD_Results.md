## 1. Исполнение и подтверждение

Использованы 20 синтетических `conversation.user` Events, прошедших штатный Runtime, пять сформированных Memories, двадцать подтверждённых source links и один frozen snapshot на сравнение. Отдельный SQLite FTS5 индекс является **только лабораторной проекцией**; Core, EventLog, MemoryStore и Knowledge не изменяются.

32 запроса (8 исторических G1, 20 точных marker-запросов, 4 дополнительные пробы), 4 варианта A/B/C/D, 4 бюджета: **512 парных сравнений**. Единые FTS5-tokenization/query parser, BM25 в одной таблице, детерминированный tie-break, общий JSON renderer и подсчёт фактически сериализованных символов. Gold фиксируется как реальные Event ID из Runtime, не как подстроки результата.

**CI:** по всем трём версиям Python профильный прогон **63 passed**, полный **1490 passed**, `scripts/check.sh` PASS, импорт `build_core` PASS. Не было новых тестовых отказов на указанном SHA. Проведены отдельные negative checks для source integrity, snapshot drift, parser injection, packed budgets и double-writer ledger.

## 2. Результаты при 10 items / 1200 chars

Знаменатель **45** — сумма количества релевантных Event-ID попаданий по положительным запросам; это не 45 различных исходных Events.

| Вариант | Direct Event-ID hits | Reachable Event-ID hits (direct или через links из выбранных Memories) | Строгие нецелевые Events в положительных ответах |
| --- | ---: | ---: | ---: |
| **A — Memory-only** | 0/45 | 24/45 | 0* |
| **B — Event-only** | **41/45** | **41/45** | 15 |
| **C — Event+Memory flat** | 40/45 | 40/45 | 15 |
| **D — C + one source hop** | 36/45 | **43/45** | 39 |

`* A` возвращает только Memory, поэтому ноль прямых Events **задан контрактом**; показатель «0 нецелевых Events» также нельзя трактовать как отсутствие ложной Memory-релевантности.

**Reachable ≠ displayed:** ссылки из выбранной Memory могут указывать на исходные Events, которые **не вошли** в ограниченный сериализованный контекст. Поэтому 43/45 для D — преимущество в доступности происхождения, а не доказательство того, что ANIMA непосредственно получила 43 исходных свидетельства.

**«Нецелевой Event»** — Event, отсутствующий в узком gold конкретного запроса; он может быть контекстным событием того же эпизода, а не ложным фактом мира.

## 3. Чувствительность к бюджету

| Бюджет items/chars | A: source reachable | B: direct | C: direct | D: direct | D: source reachable |
| --- | ---: | ---: | ---: | ---: | ---: |
| 3/256 | 3/45 | 28/45 | 28/45 | 28/45 | 28/45 |
| 3/1200 | 24/45 | 33/45 | 32/45 | 30/45 | 43/45 |
| 10/256 | 3/45 | 28/45 | 28/45 | 28/45 | 28/45 |
| 10/1200 | 24/45 | **41/45** | 40/45 | 36/45 | **43/45** |

На 256 chars фактически ограничивает размер готового JSON, а не `max_items`; короткие первичные Events проходят, крупные Memory summary не помещаются. При 1200 chars D тратит места на связанный контекст, увеличивает provenance coverage, но снижает прямой Event-ID recall.

Из 20 точечных `id_lookup` все **20/20** отданы из SQLite-индекса по настоящему Event ID; это **отдельная проверка доступности**, не то же самое, что бюджетированный поисковый запрос. Два смысловых парафраза без лексического перекрытия не нашли gold Event ни одним вариантом. Строгий `no_match` не вернул результатов; специальный adversarial negative с общим словом `telemetry` дал ожидаемые лексические false positives. Это записано как измеренное ограничение, а не «исправлено» подгонкой теста.

## 4. Решение и применимость

1. **Выбрать B (Event-only SQLite FTS5)** как начальный базовый канал поиска исходных Events; оставить прямой Event ID lookup.
2. **Сохранить Memory retrieval отдельно** для поиска эпизодов; **не** автоматически смешивать Memory и Event в один контекст без отдельной политики бюджетов/рангов.
3. **Сохранить прямые source links** как возможность проверить provenance и по запросу расширить эпизод. **Не включать D в default retrieval**: на этом корпусе он не улучшает непосредственно выбранное первичное свидетельство и усиливает загрязнение ограниченного контекста.
4. **Не вводить сейчас графовую СУБД и embeddings**. Парафразы выделить в следующий отдельный semantic retrieval EXP с независимой разметкой и ресурсными измерениями. Не считать FTS5 семантическим поиском.
5. **Переходить к шагу 2 Memory Roadmap — Event Retrieval v1**: derived FTS5 с rebuild/replay, точечным lookup, source/temporal metadata, индексным cursor и явной incomplete/error семантикой. Production interfaces и schema менять только по отдельному техническому заданию.

## 5. Границы доказанного

- 20 искусственных пользовательских сообщений — не поток доверенных сенсоров, не независимая проверка Knowledge, не обучение и не полноценная когнитивная память.
- Измерены ограниченные queries и SQL/JSON context packing, **не** 10³–10⁵ событий, p99 под нагрузкой, долговечность накопителя или многопроцессная запись в сырой JSONL.
- Хэши frozen snapshots между независимыми CI-запусками могут отличаться из-за времён и UUID; сравнение A/B/C/D проводится **внутри одного снимка**. Числовые результаты на Python 3.12/3.13/3.14 совпали.
- Это решение о **первом поисковом канале**, не утверждение, что графовые отношения бесполезны для будущей причинности, Knowledge или задач ANIMA.

**Итог:** EXP-009 Stage 1 достиг своего узкого исследовательского gate. Выбор baseline: **Event FTS5 + отдельное Memory/Knowledge retrieval + provenance on demand**. Следующее измерение — ресурсный C3 и интеграционная приёмка Event Index на PC/Pi 5.
