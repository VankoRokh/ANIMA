# EXP-009 — Stage 1: Controlled Retrieval A/B/C/D

**Статус:** техническое задание принято к подготовке; экспериментальный код и новая приёмка ещё не выполнены.  
**Дата:** 2026-11-11.  
**Ветка:** `experiment/core-memory-information-baseline`.  
**Основания:** [Memory Roadmap](Memory_Architecture_v1_Roadmap.md), [EXP-009](Research.md), [G1 laboratory](../../labs/exp009/c2_graph_compare.py), [G1 probe](../../labs/exp009/graph_memory_probe.py), [G1 tests](../../tests/test_exp009_g1_graph_memory.py), [Stage 0 gate](Memory_Stage0_Baseline_Remediation_Brief.md).

## 1. Исследовательский вопрос

**При одинаковых исходных данных, запросах, бюджете и правилах упаковки увеличивает ли проход по существующим прямым source links точность извлечения первичных Events относительно плоского FTS5?**

Предыдущее G1 показало 22/22 буквальных target markers у графовой схемы при 10 items/1200 chars уже на глубине 0; Event-only FTS5 повторил это покрытие в контрольной проверке. Это **не** результат независимого семантического benchmark и не доказательство пользы графа: G1 использовал разные точки входа и упаковку для штатного A и графового B. В новом эксперименте сравнение должно быть парным.

## 2. Четыре экспериментальных варианта

| Вариант | Кандидаты до упаковки | Дополнительные переходы |
| --- | --- | --- |
| **A — Memory-only FTS5** | Лексический поиск по снимку `Memory.content` | Нет. Путь к raw Event не добавляется автоматически. |
| **B — Event-only FTS5** | Лексический поиск по явно доступному тексту первичных `conversation.user` Events | Нет. |
| **C — Event + Memory FTS5** | Слияние независимых лексических каналов; дубликаты ID не повторяются | Нет. |
| **D — C + source hops** | Те же seeds, query parser, ranking и исходный пул, что у C | Только типизированные `Memory → Event` и `Event → Memory` по реальным `memory_sources`, в выбранном направлении, один hop. |

**Отдельный референс:** штатный `RetrievalEngine + ContextBuilder FAST/DEEP` из G1; выводить его в отчёте, **но не подменять им** A в парном сравнении. Knowledge и гипотетические семантические рёбра в новом G1-корпусе отсутствуют и не должны добавляться искусственно ради результата.

## 3. Входные данные: freeze и provenance

1. Использовать **один** неизменяемый снимок из 20 пользовательских сообщений C2-C/F/G1, сохранённых штатным Runtime; фиксировать исходный commit, хэши manifest, seed, набор Event IDs, Memory IDs, 20 `memory_sources`, timestamps и canonical sort.
2. Создавать снимок в отдельном `tmp_path`, не трогая рабочий экземпляр; индекс и графовые проекции — только лабораторные.
3. Учитывать служебный `system.wake` как сохранённый Event, но не индексировать его как пользовательское свидетельство в основных поисковых профилях; отразить выбор фильтра в report.
4. Каждый gold marker связывать с **конкретным** `Event ID`; не оценивать только наличие текстовой подстроки в сгенерированном пакете. Для исторической сопоставимости отдельно сохранять `literal_marker_hits`.
5. Если разные прогоны создают новые UUID/времена, выполнить все четыре варианта **на одном frozen snapshot** и сравнивать ID внутри него, а не объявлять произвольные повторные экземпляры побайтно идентичными. Зафиксировать детерминированные tie-breaks.

## 4. Запросы и gold

**Существующий набор G1:** восемь поисковых запросов, включая `no_match`; имена и target markers брать из `QUERIES` лаборатории без изменения ожидаемых соответствий.

**Новые независимые проверки:** не менее двадцати точных lookup по Event ID/уникальному маркеру; отдельно размеченные парафразы (термин в запросе может отсутствовать в raw тексте), отрицания, числа/единицы, соседние события, шум, одинаковый timestamp, похожие Entity и ошибочно правдоподобные совпадения. Для парафраз не использовать хрупкие подстрочные ожидания; gold — множество Event IDs с явной причиной релевантности.

**Разделять:** `id_lookup` (проверка доступности), `lexical_discovery` (поиск кандидатов), `semantic_paraphrase` (проверка ограничения лексики) и `no_match` (false positives). Не объявлять провал FTS по непересекающимся парафразам реализационным дефектом: это измерение возможностей канала.

## 5. Инварианты сравнения

- **Query parser:** один для B/C/D и лексической части A; взять `GraphMemoryProbe._fts_query` как отправной контракт; явно учитывать RU/EN, регистр, ID, числа и экранирование MATCH. Gold и query IDs не включать в поисковый текст незаметно.
- **Rank:** фиксированные сортировка и tie-break. Для смеси B/C использовать согласованное объединение рангов каналов (например, RRF с неизменной константой) либо один общий индекс и обосновать сравнимость баллов. **Не складывать raw BM25 из разных индексов без нормализации.**
- **Budget:** параллельно проверять `3/256`, `3/1200`, `10/256`, `10/1200` (items/символы); одинаковые правила подсчёта **готовой сериализованной выдачи**, порядок упаковки и механизм truncation. Изменения в контекстном формате влияют на результаты и должны версионироваться.
- **Source hops:** D расширяет только после идентичного seed retrieval, при лимитах `max_hops=1`, `max_visits`, `max_edges_per_node` и общем итоговом бюджете. Позиция и причина расширения должны быть видны в ответе. Сравнивать при **одинаковом** max_items/max_chars, не давать D бесплатных дополнительных записей.
- **Fairness:** одинаковый snapshot, одинаковое разрешение event fields, токенизатор, event-type фильтр, ID gold и предсказуемый порядок. Отдельно отражать случаи, где Memory занимает слот, вытесняя raw Event. Ни один вариант не получает доступ к gold при поиске.
- **No LLM:** поиск и оценка не требуют модели/облака.

## 6. Метрики и raw output

Для каждого (query, method, budget) записать: `query_id`, `target_event_ids`, `selected_event_ids`, `selected_memory_ids`, `seeds`, `source_paths`, `hits`, `false_positives`, `misses`, `precision_at_k`, `recall_at_k`, `chars_used`, `items_used`, `truncated`, `visits`, `latency_ms`, `snapshot_hash`, `parser_version`, `renderer_version`.

- `recall_at_k = relevant selected Events / relevant gold Events` для запросов с непустым gold. `precision_at_k = relevant selected Events / selected Events`, определение Memory-only candidate precision по отдельной метрике; **не** выдавать его за Event precision.
- Для `no_match` `recall` математически не определён; записать `false_positive_count` и `no_match_pass` вместо 0/0.
- Измерять точный `Event-ID recall` отдельно от текстового `marker coverage`; последняя метрика историческая, не является доказательством смысловой точности.
- Отчёт должен содержать **сырой ranked list** и причины/путь каждой выбранной записи наряду с агрегатами, чтобы можно было разбирать ошибки без доверия единственному score.
- Указывать `unsupported`, `partial` или бюджетный отказ отдельно от отсутствия совпадений.

## 7. Отрицательные проверки

1. Query parser с одиночными буквами, кавычками, SQL-like вводом и нелатинскими токенами не приводит к инъекции или аварии.
2. `no_match` не даёт случайной выдачи.
3. Raw Event, отсутствующий в Memory summary, остаётся доступным в B/C/D.
4. Подменённая source link или Event ID не преобразуются в новое доказательство.
5. Повторная индексация одного frozen snapshot не меняет состав/порядок результата; не мутирует EventLog/MemoryStore.
6. При бюджете 3 items D не выдаёт 4 записи; превышение ограничений сообщает точную причину.
7. Переходы D не дают независимых Evidence голосов из дублей и не меняют достоверность источника.
8. Изменение времени или случайного UUID при другом экземпляре не маскируется заявлением о повторяемости одного снимка.

## 8. Условия решения

**Переход к Event Retrieval v1** возможен, если плоский индекс обеспечивает прямой ID lookup, воспроизводимый поиск сырого Event и восстановление provenance, без потери исходных данных.

**Принимать source hops** только при измеримом улучшении Event-ID Recall/Precision или снижении стоимости для заранее согласованного класса запросов на равном бюджете. При нулевом выигрыше D отложить; не заменять существующие `LinkStore`/связи, но не добавлять глубокую BFS ради «графовости».

**Семантические embeddings** рассматривать отдельным EXP после документированных ошибок на парафразах. Результаты на 20 синтетических сообщениях — функциональный baseline, не доказательство масштабируемости или понимания.

**Stage 1 gate:** протокол frozen snapshot, реализованные A/B/C/D, формальные gold и raw output, негативные тесты, отчёт и репродукция. Статус пока **OPEN**. Работаем в лаборатории: `anima/memory`, `project.json`, `KnowledgeLayer` и production routing на этом этапе не менять.
