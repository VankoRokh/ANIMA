## 1. Цель и критерий первой работоспособной версии

Первая версия ANIMA Core должна самостоятельно, **без LLM, Godot, графического интерфейса и сети**, выполнить многократный воспроизводимый цикл:

`Observation/Event → validation/record → Belief update → Goal/Task evaluation → bounded decision → Policy → Action → independent Observation/Verification → next turn`.

Система должна сохранять идентичность, причинную историю, актуальные убеждения и незавершённые задачи при перезапуске. Если возможностей, данных или разрешений недостаточно, она должна корректно остановиться, запросить наблюдение или отложить задачу; отсутствие LLM не является аварией ядра.

**Первый проверочный контур:** малый in-process test-world adapter с дверью и зарегистрированными операциями. Это тестовый doubles/harness, **не** реализация будущего игрового движка. Для проверки Core не требуется перемещение по двумерной карте: навигация — отдельная подключаемая способность.

**Выход этапа:** runnable headless Core, отдельная приемочная матрица сценариев и representative report. Число классов, файлов и тестов не используется как метрика интеллекта.

## 2. Инварианты и границы ответственности

1. **System ownership.** Identity, lifecycle, event persistence, belief write policy, Goals/Tasks, access policy, execution, verification и recovery остаются под управлением системы. Предложение модуля не является разрешением или подтверждённым фактом.
2. **Минимальная детерминированность.** При равных верифицированных входах, конфигурации, стартовом состоянии, версиях схем и виртуальном времени переходы Core воспроизводимы. Реальные часы и I/O должны вводиться через контролируемые интерфейсы; возможные nondeterministic источники фиксируются в trace.
3. **Разделение видов данных.** История Event, Observation (что сообщил источник), рабочий Belief, более устойчивое Knowledge, Hypothesis, Task/Goal и Result — не одно хранилище истины и не один enum.
4. **Границы осведомлённости.** Обновление Belief происходит по доступным наблюдениям и определённым правилам. World ground truth испытательного стенда не передаётся Core, если он недоступен через зарегистрированный observation adapter.
5. **Время и provenance.** Время события, время получения, область действительности, источник и producer различаются. Поздно доставленное старое событие не перезаписывает новое убеждение автоматически. Отсутствие наблюдения не доказывает отсутствие объекта.
6. **Авторитет операций.** Прямой write model output в состояние, задачи, Knowledge и executor запрещён. Проверка preconditions повторяется непосредственно перед потенциальным эффектом. Receipt != проверенный успех.
7. **Непрерывность без busy loop.** Core пробуждается от событий, таймера, результата операции или необходимости работы; idle не должен требовать постоянной генерации мыслей. Есть ограничения на число шагов/действий/повторов и понятные причины defer/stop.
8. **Восстановление без ложной гарантии exactly-once.** После неопределённого исхода внешнего действия Core сначала согласует состояние или использует явно идемпотентный контракт; нельзя автоматически повторять произвольный эффект.
9. **Модульность.** Навигация, pathfinding, правила конкретного мира, восприятие изображений, LLM, сложное прогнозирование, обучение, эмоции, интерфейс и игровые механики — не код Core. Core может использовать зарегистрированную способность, но не должен требовать её для базовой работоспособности.
10. **Переиспользование прежде переписывания.** Исторический Stage 4 Planner остаётся legacy. Проверенные Stage 0–3 и Stage 5–6 механизмы инвентаризируются и адаптируются; новая параллельная система не создаётся без доказанной необходимости.

## 3. Функциональный состав Core v0.1

Здесь перечислены **ответственности**, не требование создавать отдельный пакет или процесс:

| Ответственность | Что обязательно в v0.1 | Отправная точка |
|---|---|---|
| Identity / lifecycle | постоянный instance id, запуск/остановка, управление режимом | Stage 0, `anima/core/state.py` |
| Runtime / events | типизированный ingress, идентификаторы, журнал, bounded dispatch | `anima/runtime.py`, EventBus и EventProcessingCoordinator |
| Persistent system state | атомарные в допустимых границах изменения, версии, recovery | State/MemoryStore и существующие stores |
| Belief state | текущая версия представления, scope/time, evidence refs, unknown/stale/disputed, ревизии | новая узкая проекция поверх принятой семантики |
| Tasks / Goals | заданная внешняя цель, bounded tasks, разрешённые follow-ups, завершение/приостановка | Stage 6 Tasks / Goals |
| Decision / policy | минимальные правила выбора и допустимости; abstain/observe/defer | deterministic resolver, Choice/operation policy |
| Executor / verifier | зарегистрированная операция, precondition, receipt, независимая проверка | Stage 6 Execution / Verification |
| Trace / recovery | causal IDs, аудит решений, restart reconciliation | UnifiedTrace и recovery |

Полный Stage 7 knowledge write/lifecycle не объявляется реализованным: действующие DP-08, DP-09, DP-10b и DP-11 остаются открытыми. Для Core v0.1 допустим **узкий belief update policy для явных структурированных наблюдений**, не универсальная семантическая редакция Knowledge.

Семантика Scope/Source/Producer/Evidence, принятая в Stage 7 read-only boundary, не должна молча переопределяться.

## 4. План реализации и проверяемые выходы

### P0 — Boundary / reuse audit

- Зафиксировать dependency map активных путей: `runtime → events → memory/belief → task/decision → action/verification → recovery`.
- На каждый необходимый механизм указать: переиспользовать / минимально изменить / добавить; запретить второй competing ownership path.
- Сформулировать тестовые схемы Event, Observation, BeliefUpdate, Action, Verification и Capability; определить только необходимые поля, версии и ошибки.
- Снять baseline регрессионных проверок `scripts/check.sh` и `pytest` на закреплённом commit, зафиксировать ограничения.

**Выход P0:** принятая Boundary/Acceptance spec и проверенный список точек повторного использования.

### P1 — Standalone Core startup

- Запускать Core без model backends, сети и графики; lifecycle, persistent identity, контролируемое завершение.
- Подключить минимальный in-process adapter, возвращающий типизированные observations и принимающий зарегистрированные test-actions.
- Проверить idle/wakeup, ограничения очереди и trace.

**Gate P1:** автономный запуск и остановка; отсутствие обязательных зависимостей от LLM/Godot; базовые события проходят через один system-owned ingress.

### P2 — Observation → Belief

- Создать небольшую версионируемую проекцию рабочего состояния без прямого доступа к test-world ground truth.
- Поддержать обновление из явного структурированного observation и статус unknown/stale/disputed при недостатке или конфликте оснований.
- Сохранять ссылку на источник и основания, различать source observation time и receipt time.
- Проверить duplicate/redelivery, out-of-order timestamps, неизвестность, пропуски и конфликт.

**Gate P2:** воспроизводимое изменение Belief из контролируемых observations; предыдущая информация не исчезает из истории; absence != false; прежний report не становится новым фактом из-за времени доставки.

### P3 — Bounded autonomous action loop

- Задать одну или несколько **внешне установленных** целей с механически проверяемым условием.
- Из ограниченных правил разрешить порождение follow-up задач типа `observe / approach_if_capability_available / operate / verify / defer`.
- Выполнять действие только через типизированный зарегистрированный capability/action adapter, с повторной проверкой preconditions.
- Сохранять явные `proposed → permitted/rejected → attempted → receipt → verified/not_verified` причины.
- Реализовать остановку при недостатке данных, исчерпании лимита и отсутствии прогресса.

**Gate P3:** дверь при известном открытом состоянии закрывается и проверяется; уже закрытая не трогается; изменение до исполнения отменяет ненужный эффект; ни один failure receipt не считается успехом Goal.

### P4 — Durability, recovery, regression

- Проверить перезапуск в состоянии idle, после регистрации события, перед действием, после возможного эффекта, но до проверки.
- Проверить re-delivery и повторную обработку; после uncertain action не выполнять слепой повтор.
- Добавить headless сценарии со смешанными событиями, шумом, неизвестностью и конкурирующими задачами.
- Автоматически получать machine-readable events/decisions/action/belief traces и читаемый result report.

**Gate P4:** Core v0.1 считается **первично работоспособным** только после прохождения принятой матрицы no-LLM сценариев, отсутствия запрещённых эффектов и подтверждённого восстановления в проверенных fault classes. Отдельно фиксируются не покрытые реальные power loss/OS/sensor failure cases.

### P5 — Independent Virtual Lab feasibility (после P4; исследовать можно раньше, но не блокировать Core)

- Выбрать готовую основу, приоритетный кандидат Godot, резервный MultiGrid; не создавать собственный игровой движок.
- Проверить два одновременных независимых актора: `Human` управляется пользователем с клавиатуры, `ANIMA` — отдельным Python test-controller. Человек не «перехватывает» управление ANIMA.
- Проверить движение, столкновения, объекты, скриптуемые события, runtime вмешательство пользователя, паузу/step и визуальную инспекцию.
- Отделить World State (ground truth) от observations; закрепить adapter и protocol versions; записывать human input и сценарный seed/тайминг.
- Подтвердить headless execution, logs и replay команд (с документированным уровнем детерминизма).

**Gate P5:** отдельный полигон с двумя управляемыми сущностями, Python bridge и логами работает **без ANIMA Core**.

### P6 — Core ↔ Virtual Lab integration

- Заменить in-process test adapter на versioned bridge к выбранному полигону; сценарная логика остаётся в Lab, ownership действий — в Core.
- Навигацию/поиск пути подключать как capability; Core видит её типизированные входы, выходы и лимиты, не конкретный grid/pathfinder.
- Провести автоматические и интерактивные прогоны; пользователь может самостоятельно перемещать Human, открывать двери, блокировать проходы и вызывать изменения.
- Визуально показывать различие `World State` и `ANIMA Belief` только разработчику, не раскрывая ground truth агенту.

**Gate P6:** один и тот же класс сценариев проходит через in-process adapter и выбранный Lab adapter при эквивалентных наблюдениях/действиях; отсутствие изображения/человека не разрушает Core.

## 5. Матрица сценариев (семейства, а не один демонстрационный тест)

| Семейство | Пример | Какие свойства проверяются | Обязательность для P4 |
|---|---|---|---|
| T0 — базовые переходы | дверь открыта / уже закрыта | корректная цель, отсутствие лишних эффектов, receipt vs verification | Да |
| T1 — устаревшая информация | дверь закрыта другим актором до исполнения | обновление Belief, повторная precondition проверка, отмена | Да |
| T2 — доставка наблюдений | дубликат, задержка, out-of-order, неизвестная информация | idempotence, time, unknown, provenance | Да |
| T3 — ошибки и восстановление | отказ действия, restart, lost reply/uncertain outcome | bounded retry, reconcile, recovery | Да |
| T4 — шум и одновременные события | несколько несущественных событий плюс значимое | внимание к goal-relevant фактам, отсутствие starvation | Да, минимальный набор |
| T5 — пространственные варианты | дверь далеко, обход препятствия, заблокированный проход | контракт навигационного capability и работа с изменением маршрута | После P5/P6 |
| T6 — человек в мире | Human открывает дверь, передвигает препятствие | interactive observation, dual actor, корректные выводы | После P5/P6 |
| T7 — расширения | дополнительные комнаты, предметы, сценарии без правки ядра | конфигурационная расширяемость | После P5/P6 |

Каждое обязательное семейство должно включать **несколько независимых вариантов**; минимум: обычный положительный случай, отрицательный/граничный и изменённый порядок/условия, если применимо. Полный список fixtures, точные метрики и пороги фиксируются **до** итогового acceptance run. Критично: ни одного запрещённого действия или неправомерно подтверждённого Goal в испытанной матрице. Скоростные пороги — после baseline измерения, не произвольно.

## 6. Test harness, visualizer и отчётность

- Тесты Core: `pytest` + временное isolated data directory и управляемое логическое время. Без обязательной GUI/LLM.
- Каждый прогон: сценарий, fixture/version, seed, build/commit, start/end state, event timeline, observation provenance, belief revisions, decisions, policy verdicts, action receipts, verification и errors.
- Форматы: machine-readable per-run trace и читаемый Markdown summary. Имена файлов являются деталями реализации; требуется структура и связность записей, а не несколько дублирующих источников.
- Human input записывается как отдельный тип externally-originated commands; replay не означает, что ANIMA получила privileged state.
- В Git сохранять только representative results по принятому стилю `docs/TESTING/Results/TV-xxxx.md`. Полные transient logs — вне version control, если не определено иное.

## 7. Не входит в Core v0.1 / в эту итерацию

Нет: универсального Knowledge revision/write lifecycle, LoRA/SFT, самостоятельного свободного целеполагания, новых прав models, сложных эмоциональных схем, прогнозирующей world model, CV/audio hardware, физической навигации, self-modifying production code и обязательной системы Sleep consolidation.

Поддерживаемые режимы lifecycle и разрешённые maintenance hooks допустимы, но фоновые интеллектуальные работы остаются подключаемыми. Legacy Stage 4 не возвращается как top-level planner.

## 8. Решения и риски до реализации

1. **P0 blocking:** конкретный Belief write policy для структурированных событий (что считается observation, как маркировать conflict/unknown/stale, как не узурпировать Stage 7 Knowledge semantics).
2. **P0 blocking:** совместимость существующих Stage 6 Task/Goal/Executor contracts с одним автономным event loop, без второй конкурирующей управляющей ветви.
3. **P0 blocking:** транзакционная граница и модель uncertain external effect/reconciliation; гарантия не должна быть сильнее покрытых fault tests.
4. **До P5:** сравнить поддерживаемые версии/лицензии/демопроекты Godot и альтернативы, включая интерфейс Python и headless режим; выбор Godot остаётся кандидатом, пока feasibility gate не пройден.
5. **До P6:** проверить, что наблюдения Human/ANIMA привязаны к actor identity, timestamp и world revision; world renderer не имеет системных полномочий.
