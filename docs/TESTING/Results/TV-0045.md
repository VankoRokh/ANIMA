# Stage 6.1–6.2b Coordinator, FAST/DEEP routing and first DEEP backend

## Цель

Подтвердить system-owned cognitive orchestration после Persistent Task baseline: Coordinator связывает Task с CanonicalTask/resolution, Router выбирает FAST/DEEP до model call, Dispatcher вызывает только выбранную роль, а первый реальный DEEP backend остаётся сменяемым и не получает ownership над Task/Goal/Memory/routing.

## Условия

Проверенный snapshot: `fc3f56c28fa9da9aca5fdaa44dd8e31cdeae0e64` в ветке `work/stage6-cognitive-integration`.

Первый experimental DEEP profile: `SmolLM3-3B-Q8_0`, thinking disabled, temperature 0, top-k 40, top-p 0.8, min-p 0.05, max output 256. Модель является конфигурацией `DeepLLMProfile`, а не частью DEEP contract.

FAST и DEEP используют общий `TextTransport` / `LlamaCppTransport`; role-specific backend/prompt остаются отдельными.

## Сценарий и входные данные

Проверены следующие границы и сценарии:

- persistent Task → Coordinator → CanonicalTask → deterministic resolution;
- обычный open cognitive remainder → FAST;
- explicit evidence conflict → DEEP;
- system route выбирается до model call и сохраняет reason/policy version;
- Dispatcher вызывает только выбранный backend;
- FAST/DEEP возвращают `CognitiveProposal` без мутаций persistent stores;
- в model-backed baseline принимается только `RESPOND`; `PROPOSE_ACTION`, `PROPOSE_TASK` и `REQUEST_CONTEXT` остаются disabled;
- action-choice path не передаётся FAST/DEEP;
- controlled DEEP failure не вызывает автоматический fallback в FAST и не мутирует Task;
- замена `SmolLM3-3B-Q8_0` на другой `DeepLLMProfile` не меняет Router/Dispatcher/Proposal contracts;
- общий llama.cpp transport не меняет Stage 5 compatibility imports;
- реальный opt-in SmolLM3 smoke проходит production Router → Dispatcher → DeepLLMBackend path.

Команды проверки включали targeted Stage 6/transport suites, `bash scripts/check.sh`, полный `.venv/bin/python -m pytest -q` и opt-in `scripts/run_stage6_deep_smoke.py`.

## Ожидаемый результат

Система, а не LLM, выбирает cognitive role; DEEP является сменяемым backend и не владеет orchestration/persistence; failure isolation сохраняется; общий transport не ломает FAST; реальная SmolLM3 проходит bounded conflict smoke.

## Фактический результат

Все targeted проверки, project checks, полный regression suite и реальный SmolLM3 smoke прошли успешно на указанном snapshot.

## Метрики

Acceptance для этого slice бинарный и архитектурный: targeted suites, project checks и полный regression должны быть зелёными; DEEP smoke должен завершиться через DEEP route без FAST call; controlled DEEP failure не должен менять Task; backend replacement должен сохранять тот же request/proposal contract. Benchmark v2 latency SmolLM3 не используется как Stage 6 SLA.

## Доказано

Stage 6 имеет рабочие system-owned границы `Task → Coordinator → Resolution → Router → FAST/DEEP → CognitiveProposal`. Первый DEEP backend можно заменить без изменения архитектурных контрактов. FAST и DEEP не получают прямого доступа к persistent ownership или execution.

## Не доказано

Эта проверка не доказывает выбор между action candidates через Goal/Internal State, execution/verification integration, Sleep lifecycle integration, integrated restart recovery или superiority SmolLM3 над другими DEEP-кандидатами. SmolLM3 остаётся первым experimental candidate, а не закреплённым backend.

## Итог

Stage 6.1–6.2b принят как рабочий FAST/DEEP baseline. Следующий slice — 6.3 Goals + Internal State + Choice: system-owned action selection без передачи FAST/DEEP authority над выбором действия.
