# Stage 3.6 Chunk / Checkpoint / Resume

## Цель

Подтвердить persistent chunk checkpoints и безопасный resume: committed chunk после interruption/restart не выполняется повторно, а resumed run даёт тот же допустимый результат, что непрерывный.

## Условия

Проверенный snapshot: `ef1c7942c7130aaf22ca6a4db1fef6fb1e3f3778`. Проверка выполнена владельцем проекта в локальном checkout.

## Сценарий и входные данные

```bash
.venv/bin/python -m pytest -q tests/test_sleep_checkpoint_resume.py
.venv/bin/python -m pytest -q \
  tests/test_sleep_storage.py \
  tests/test_sleep_contracts.py \
  tests/test_sleep_selection.py \
  tests/test_sleep_processors.py \
  tests/test_sleep_text_consolidation.py \
  tests/test_sleep_checkpoint_resume.py
.venv/bin/python -m pytest -q
bash scripts/check.sh
```

Canonical tests используют ordered chunks, interruption после разных committed checkpoints, reopen того же `sleep.db`, реальный `DeterministicTextConsolidationProcessor`, повреждённую checkpoint metadata и миграцию существующей schema v2 в v3.

## Ожидаемый результат

- checkpoint и его `local_result` фиксируются атомарно;
- `WorkItem.checkpoint_ref` указывает на последний persisted checkpoint;
- после reopen executor начинает со следующего незавершённого chunk;
- committed chunks не передаются processor повторно;
- interrupted/resumed и uninterrupted run эквивалентны по final output;
- повреждённая checkpoint metadata блокирует resume явной ошибкой;
- существующий `sleep.db` schema v2 мигрирует в v3 без потери WorkItem.

## Фактический результат

Targeted `tests/test_sleep_checkpoint_resume.py` завершился результатом 12 passed. Combined Sleep suite 3.1–3.6 дал 82 passed. Полный `pytest -q` и `scripts/check.sh` также прошли успешно; точное число полного regression suite отдельно не фиксировалось.

## Доказано

Chunk считается завершённым только после persisted checkpoint; checkpoint state и локальный результат переживают reopen. Resume пропускает уже committed sequence и продолжает со следующего. Реальный deterministic-text processor после interruption/reopen даёт тот же содержательный output, что непрерывный run. Migration v2 → v3 сохраняет существующие WorkItems.

## Не доказано

Stage 3.6 не восстанавливает автоматически WorkItem, оставшийся `running` после аварийного завершения процесса, и не координирует эффекты между `sleep.db` и Cognitive Memory storage. Persistent DerivedResult/provenance проверяется отдельно в Stage 3.7; crash/replay idempotency внешних эффектов относится к Stage 3.8.
