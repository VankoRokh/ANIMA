# Stage 3.12 Performance Baseline

## Цель

Измерить стоимость Sleep orchestration на реальном текущем стенде без заранее заданного SLA: отдельно selection/scheduling, checkpoint/history, derived-result/provenance и 10 GiB synthetic large-source workload. Зафиксировать scaling bottlenecks до оптимизации.

## Условия

Проверенный snapshot: `be862fddb4d5dd4de734ad322017b72da2bc6346`.

Локальный стенд владельца проекта:

- Python 3.14.4;
- Linux 7.0.0-38-generic x86_64, glibc 2.43;
- 8 logical CPUs;
- 15290.711 MiB total RAM;
- benchmark worker для каждого тяжёлого case запускается отдельным процессом.

Benchmark: `scripts/benchmark_stage3.py`, размеры 1k/10k/100k WorkItems, 5 samples для обычных cases, checkpoint history depth 128, synthetic large source 10 GiB с chunk size 5 MiB и interruption после 512 chunks.

## Сценарий и входные данные

```bash
.venv/bin/python -m pytest -q tests/test_sleep_performance.py
.venv/bin/python scripts/benchmark_stage3.py
.venv/bin/python -m pytest -q
bash scripts/check.sh
```

Synthetic seeding выполняется вне измеряемой production operation. Selection измеряет `SleepSelector.select()` на уже существующей очереди; checkpoint — commit/latest/history на масштабированной `sleep.db`; provenance — `DerivedResultRepository.commit_final_result()`; large-source — реальный `SleepChunkExecutor` с interruption, reopen и direct resume.

## Ожидаемый результат

- baseline 1k/10k/100k получен без crash/OOM;
- checkpoint и provenance имеют измеренную стоимость независимо от размера общей очереди;
- selection scaling виден отдельно от setup;
- storage growth измерен;
- 10 GiB logical source завершается после interruption/restart с direct resume;
- найденные bottlenecks фиксируются, но не оптимизируются внутри baseline шага;
- полный regression suite остаётся зелёным.

## Фактический результат

Benchmark завершился успешно. Selection p95 вырос от 15.0300 ms на 1k до 1774.9641 ms на 100k, при peak RSS 252.227 MB на 100k. Checkpoint commit p95 остался около 0.54–0.61 ms во всём диапазоне, provenance finalize p95 — около 1.23–1.34 ms. Storage вырос примерно линейно от 0.539 MB на 1k до 47.910 MB на 100k.

Synthetic large-source 10 GiB / 2048 chunks завершился за 1349.0693 ms с throughput 1518.08 chunks/s; resume был выполнен с checkpoint, storage составил 1.520 MB. Worker имел current RSS 135.652 MB и peak RSS 170.273 MB после завершения сценария.

После benchmark полный regression suite дал 442 passed за 6.86 s. `scripts/check.sh` прошёл полностью на Python 3.14.4.

## Доказано

Checkpoint commit и обычный provenance finalize не деградируют заметно из-за роста общей очереди до 100k WorkItems на текущем SQLite baseline. Storage растёт приблизительно линейно. Selection является текущим основным scaling bottleneck: latency и RSS заметно растут с размером очереди, но 100k workload остаётся выполнимым на текущем ноутбуке. Large-source orchestration обрабатывает логические 10 GiB, переживает interruption/reopen и завершает direct resume без materialization полного payload.

## Не доказано

Baseline не является SLA и не доказывает производительность будущих реальных video/audio/LLM processors. Checkpoint history измерена при глубине около 128, поэтому поведение одного WorkItem с сотнями тысяч checkpoints отдельно не доказано. Provenance case использует короткую transformation history и один source ref. Selection 100k требует будущего profiling/optimization только при реальной необходимости. Large-source current/peak RSS 135.652/170.273 MB требует отдельного profiling, если память станет ограничением на Stage 5/6; сам baseline не локализует источник удерживаемой памяти.
