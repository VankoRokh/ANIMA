# Stage 1.12 Performance Baseline

## Цель

Измерить без заранее заданного SLA масштабирование Stage 1 Cognitive Memory на
синтетических наборах 1k/10k/100k: Event append, storage seed, production API
операции, FTS, Relations, Retrieval, FAST/DEEP Context, EventProcessing batch,
CPU, peak RSS и размер данных. Зафиксировать bottleneck до оптимизации.

## Условия

Проверенный snapshot: `99c59c3fca78123c6ff1fdb4f70b9b07703b0ec2`.
Локальная среда владельца проекта: Linux, Python 3.14.4. Каждый размер набора
запускался отдельным subprocess, поэтому peak RSS относится к отдельному process.
Synthetic seed использует batch setup и не выдаётся за production write throughput.
Raw JSON сохранён локально в `.benchmarks/stage1-performance.json` и не коммитится.

## Сценарий и входные данные

```bash
bash scripts/check.sh
.venv/bin/python -m pytest -q
.venv/bin/python -m pytest -v -s tests/test_performance_baseline.py
.venv/bin/python scripts/benchmark_stage1.py
```

Benchmark создаёт отдельные синтетические наборы 1k, 10k и 100k, измеряет
масштаб хранения и повторяемые latency probes на заполненной базе. Отдельно
измеряется небольшой production EventProcessing batch через настоящий coordinator.

## Ожидаемый результат

- runner воспроизводимо проходит 1k/10k/100k без повреждения данных;
- фиксируются wall/CPU/peak RSS и размеры `memory.db`/общего data-каталога;
- отдельно измеряются Event append, seed throughput и production batch throughput;
- измеряются Memory create/update, Entity/Knowledge lookup, FTS, 1-hop Relation,
  Retrieval и FAST/DEEP Context p50/p95;
- обнаруженное ухудшение фиксируется как baseline, а не скрывается оптимизацией;
- по результатам можно назвать конкретные scaling bottleneck и проверить их кодовый путь.

## Фактический результат

Все три набора завершились успешно. Wall time составил 1.4579 s для 1k,
9.3665 s для 10k и 90.1241 s для 100k. Event append остался примерно стабильным
на 14.7k–15.5k events/s, synthetic seed — 37.4k–42.8k rows/s. Production
EventProcessing batch снизился с 38.50 events/s на 1k до 4.48 на 10k и 0.41 на
100k. DEEP Context вырос с p95 302.660 ms до 2398.073 ms и 23407.585 ms.

Кодовая ревизия локализовала вероятные причины: coordinator перед каждым Event
полностью читает `events.jsonl` для raw identity check, а DEEP provenance для
каждого выбранного объекта заново строит полный Event index из JSONL. Оба пути
масштабируются линейным сканированием raw log; последовательный batch coordinator
в результате приближается к квадратичной общей стоимости.

## Доказано

SQLite CRUD/lookup и 1-hop Relation baseline остаются субмиллисекундными или около
1 ms на 100k, FTS остаётся около 10 ms p95, а Event append сохраняет примерно
15k events/s. Retrieval и FAST Context растут заметно, но сохраняют интерактивный
порядок величины на 100k. Хранилище при 100k занимает около 124 MB SQLite и
152 MB полного data-каталога; peak RSS процесса достиг 265.44 MB.

Доказаны два приоритетных bottleneck: повторное полное сканирование raw Event log
в EventProcessing и повторное построение полного Event index в DEEP provenance.
Baseline сохранён до оптимизации, поэтому будущие изменения можно сравнивать с
этими цифрами, а не оценивать субъективно.

## Не доказано

Результат не является SLA и не переносится автоматически на другое железо,
файловую систему или Python version. Не измерены многопоточность, длительный
24h workload, реальные пользовательские распределения данных, model inference,
vector/graph DB и hardware target. Не доказано, что найденные bottleneck —
единственные; их устранение и повторный benchmark являются будущей оптимизацией,
а не частью исходного Stage 1.12 baseline.
