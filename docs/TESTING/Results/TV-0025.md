# Stage 3.8 Recovery / Idempotency

## Цель

Подтвердить recovery protocol Sleep для crash/replay между `sleep.db` и `memory.db`: stable logical operation key, at-least-once retry с idempotent external receipt, восстановление stale running WorkItem и отсутствие повторного применения одного логического derived effect.

Canonical recovery scenarios охватывают crash до первого checkpoint, stale `running` после committed checkpoint, падение после внешнего effect до подтверждения ledger, replay той же логической работы, повторное применение operation key и конфликтный partial operation.

## Ожидаемый результат

- logical Sleep effect получает стабильный `sop_` UUIDv5 operation key;
- `sleep.db` хранит persistent operation ledger со статусами prepared/applied/failed;
- `memory.db` хранит idempotent receipt по той же operation key;
- crash между external effect и ledger acknowledgement восстанавливается без второго effect;
- повтор той же логической работы не размножает receipt;
- stale running WorkItem без checkpoint возвращается к `queued`, а с валидным checkpoint — к `checkpointed`;
- конфликтные или неполные состояния остаются диагностируемыми;
- receipt не создаёт Memory/Knowledge и не повышает authority derived output.

## Доказано

Sleep использует persistent operation ledger и idempotent external receipt для согласования эффектов между `sleep.db` и `memory.db` без общей физической транзакции. Повтор после crash способен обнаружить уже применённый effect и завершить ledger без дублирования. WorkItem, оставшийся в `running`, восстанавливается к последней доказанной безопасной границе. Один логический effect не применяется повторно при replay.

## Не доказано

Stage 3.8 не связывает recovery protocol с общим lifecycle Runtime: ordinary sleep, активный SleepJob, wake interruption и resume пока существуют как отдельные механизмы. Это является предметом Stage 3.9 Runtime Integration. Observability/resource budget и large-data readiness остаются последующими шагами Stage 3.
