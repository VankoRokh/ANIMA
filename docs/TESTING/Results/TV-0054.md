# Raspberry Pi 5 / PC — Core v0.1 Performance, Scaling and SIGKILL Recovery (T6–T9.5)

## Цель

Проверить переносимость зафиксированного Core v0.1 на Raspberry Pi 5 (ARM64), корректность длительного синтетического прогона, сопоставить одинаковый сценарий с ноутбуком x86-64 и локализовать рост задержек без изменения production-кода. Это предварительное аппаратное исследование Stage 9, а не закрытие этапа.

## Условия

- **Core snapshot:** `6ffdc2e49b115968cb5309ea591fa27f1eace6f3`, ветка `release/core-v0.1`; `checkout_clean=false`.
- **Локальный незафиксированный патч:** `CoreDoorExecution.__init__: world: VirtualDoorWorld` → `world: DoorWorldPort`. На Python 3.13.5 исходная аннотация препятствует импорту; такой дефект был ранее воспроизведён в архитектурном обзоре от 2026-11-11. Патч не входил в указанный release snapshot; хеш изменённого дерева не представлен.
- **Raspberry:** Raspberry Pi 5, 8 GB, Raspberry Pi OS, Python 3.13.5, microSD; охлаждение и блок питания испытаны отдельно в аппаратной серии T1–T5.
- **Ноутбук:** Ubuntu, x86-64, SSD, Python 3.14.4 (GCC 15.2.0), отдельный checkout указанного snapshot; точная модель CPU и хеш локального патча не представлены. Сравнение аппаратных платформ предварительное.
- **Источник данных:** вывод терминала, переданный владельцем проекта 2026-11-12. Исходные JSON-отчёты и оба `.prof` остались на устройствах, не приложены к репозиторию; независимого повторного запуска автором этой записи не было.
- **Изоляция:** runner использует временные хранилища; Production Memory и экспериментальные E4/L2 не изменялись. GitHub production-код не изменялся в ходе данного исследования.

## Сценарий и входные данные

Runner: `scripts/run_core_endurance_gate.py`.

- **T6, ARM64 smoke:** `--episodes 24 --seed 131 --restart-every 11 --checkpoint-every 8 --blocked-goals 65`.
- **T7, ARM64 endurance:** `--episodes 180 --seed 131 --restart-every 11 --checkpoint-every 30 --blocked-goals 128`.
- **T8, x86-64 comparison:** точно те же параметры runner, что в T7.
- **T9, ARM64 profiling:** T7 под `python -m cProfile -o /tmp/anima-core-180.prof`; `pstats` сортировка по cumulative/self time.
- **T9.1, Pi caller attribution:** `pstats.Stats(...).print_callers()` для `load_events`, `_require_raw_event`, `_ensure_legacy_written`, `recover_proofs`, `_enqueue_bound_goals`.
- **T9.2, PC profiling and caller attribution:** тот же сценарий 180 эпизодов под `python -m cProfile -o /tmp/anima-pc-core-180.prof`; те же целевые вызовы и сортировка `pstats`; Python 3.14.4.
- **T9.3, отдельный EventLog scaling:** на обеих платформах отдельно создавались временные JSONL-журналы с 128, 512, 2048, 8192 и 16384 валидными синтетическими `world.observation`; для каждого размера — warm-up, семь измерений `EventLog.load_events()` с полной штатной валидацией, wall/CPU latency и размер файла. Отрицательные контроли — duplicate `ev_` ID и malformed JSON. Для Pi использован here-doc, на PC тот же бенчмарк в отдельном скрипте без изменения production-кода; код экспериментального скрипта в Git не внесён.
- **T9.4, Core Event Pipeline Scaling:** внешний тестовый скрипт `anima_t94_event_pipeline_scaling.py`, одинаковый на Pi и PC: `--events 1024 --checkpoint-every 128`. Реальный `build_core` с `CoreIngress`, `BeliefProjection`, outbox, `CoreEventDispatcher`, legacy JSONL и `EventProcessingCoordinator`; системно зарегистрирован тестовый источник, поочерёдные `open`/`closed` наблюдения для зарегистрированной двери; нет Goal/Task, виртуального мира, LLM или семантической Memory encoding. Каждый checkpoint содержит integrity check, receipt check и exact duplicate replay. Reopen при 512 и 1024 событиях — пересоздание компонентов в одном Python-процессе, а не аварийное восстановление.
- **T9.5, Actual SIGKILL Recovery:** внешний script `anima_t95_sigkill_recovery.py` запускает отдельный crash-worker для каждого из семи fault hooks, вызывает `os.kill(os.getpid(), signal.SIGKILL)` и требует код возврата `-9`. После гибели стартует **новый Python-процесс** для проверки инвариантов, используя тот же локальный временный storage. Платформы: PC Python 3.14.4 и Pi Python 3.13.5. Crash/restore выполнены по одному разу на сценарий на каждом устройстве.

Пример воспроизведения (из корня checkout, с описанным локальным патчем):

```bash
.venv/bin/python scripts/run_core_endurance_gate.py \
  --episodes 180 --seed 131 --restart-every 11 \
  --checkpoint-every 30 --blocked-goals 128 \
  --report /tmp/anima-rpi-core-endurance-180.json
```

## Ожидаемый результат

Все синтетические цели завершаются с независимыми подтверждениями, без повторных/неожиданных эффектов; повторное открытие хранилищ не нарушает идентичность; заблокированные цели не мешают новым. Задержки, память и размер хранилища измеряются без заранее объявленного жёсткого SLO. Рост задержек требует отдельной диагностики и не равен автоматическому FAIL по корректности.

Однако T9.3 **не изолирует вклад EventLog в задержку полного Core**, не измеряет O(N²) сквозного Event Processing и не определяет SLO для будущей ANIMA.

**Ограничения:** разные версии Python (3.13.5/3.14.4), кэш ОС, разные диски, лишь 7 повторов, единственная последовательность размеров, небольшое число отрицательных сценариев, отдельный экспериментальный скрипт не зафиксирован в Git. Для строгой регрессии потребуется закрепить точный скрипт, среды и повторить прогоны.

### T9.4 — измерение полного пути Core Observation → Legacy Event Processing

**Статус функциональной приёмки:** PASS для Pi и PC. **Производительность:** обнаружен последовательный рост latency нового Event с накоплением history. Данные получены из полного stdout пользователя за 2026-11-12, исходные локальные JSON: `/tmp/anima-t94-x86_64.json` и `/tmp/anima-t94-aarch64.json`; в Git сырые файлы не загружены. Оба устройства сообщили тот же Git snapshot `6ffdc2e49b115968cb5309ea591fa27f1eace6f3`; Python PC 3.14.4 / Pi 3.13.5. Ограниченный harness — вне production source tree. Скрипт принимает только заданный SHA и допускает локальный tracked patch в `anima/core/door_execution.py`, но не удостоверяет идентичность полного dirty tree.

**Границы выводов:** наблюдения `world.observation` успешно проходят входной typed Core, outbox и legacy Event Processing, но намеренно исключены из semantic/episodic Memory encoding. Задержки включают синхронный dispatch, legacy log и его проверку; нет Goal/Task/LLM. Изменения аппаратной платформы и Python одновременно не позволяют приписать коэффициент разницы исключительно CPU. Для доказательства устранения bottleneck необходим строго контролируемый A/B с отдельной реализацией и всеми негативными/аварийными проверками — вне текущего диалога.

### T9.5 — реальное прерывание Python-процесса с SIGKILL

**Дата:** 2026-11-12. **Источники:** полные stdout пользователя на PC и Pi и изученный внешний тестовый скрипт (18,418 байт, ранее переданный владельцу), не загруженный в Git. Локальные отчёты: `/tmp/anima-t95-x86_64.json`, `/tmp/anima-t95-aarch64.json` — их содержимое в этом отчёте не использовано напрямую. Проверен замороженный snapshot `6ffdc2e49b115968cb5309ea591fa27f1eace6f3`; локальный допустимый patch type annotation на Pi остаётся непубличным и не означает чистый checkout.

**Механика теста:** в отдельном `TemporaryDirectory` каждый сценарий создаёт crash-worker в отдельном ОС-процессе. Fault hook вызывает `os.kill(os.getpid(), SIGKILL)`; родитель проверяет `returncode == -9` и сохранённую crash-marker запись. Далее **новый отдельный Python-процесс** проверяет восстановление по durable файлам. Не используются production данные, внешнее оборудование, LLM или настоящие power-cut.

| Crash boundary | Core Events before recovery | Receipts before recovery | Recovery PC | Recovery Pi | Существенный результат |
| --- | ---: | ---: | --- | --- | --- |
| `ingress_uncommitted` (после INSERT, до COMMIT) | 0 | 0 | PASS | PASS | Некоммитнутая транзакция откатилась; событие **повторно отправлено отправителем**, затем принято и forwarded; это не автоматическое восстановление отсутствующего Event. |
| `admitted_pending` | 1 | 0 | PASS | PASS | Новый Runtime доставляет ранее закоммиченный Event из outbox. |
| `after_legacy_append` | 1 | 0 | PASS | PASS | После append идемпотентная доставка и одна legacy запись. |
| `after_legacy_projection` | 1 | 0 | PASS | PASS | Уже обработанное событие не проектируется повторно с дублированием. |
| `after_core_ack` | 1 | 1 | PASS | PASS | Признанный dispatch receipt сохраняется после нового старта. |
| `before_filtered_ack` | 1 | 0 | PASS | PASS | Недопустимое по property rule наблюдение получает `filtered`, не появляется как целевой legacy Event/Memory projection. |
| `door_after_effect` | 2 | 0 | PASS | PASS | Effect persisted before SIGKILL; post-crash восстановление завершает Goal/Task без второго эффекта. |

Для каждого `world.observation` с сохранённым source ingress (кроме откатанного pre-commit) новый процесс подтвердил: `core_events=1`, `dispatch_receipts=1`, target-legacy event count 1, `event_processing=skipped`, pending outbox empty, повторная доставка возвращает `ALREADY_SEEN`, размер legacy файла не увеличивается. `before_filtered_ack`: `disposition=filtered`, target legacy matches 0, `event_processing=null`. Две wake/extra legacy events в других измерениях не трактуются как дубли целевого события.

**Действие виртуальной двери:** до восстановления обе машины показали `world_effects=1`; новый процесс проверил ту же identity, `world_effects=1`, `operations=1`, `Goal=completed`, `Task=completed`; дополнительный `run_core_autonomous()` не создал нового эффекта. Это обоснованная one-effect гарантия **для этого одного synthetic keyed door capability** на выбранной точке аварии, не универсальное доказательство exactly-once любых внешних инструментов.

**Границы:** `SIGKILL` завершает Python-процесс, но ОС и кеш накопителя продолжают работать; это не проверка `fsync`/SQLite durability при потере питания, не тест произвольного случайного момента kill, не crash внешнего worker процесса, не проверка заполнения диска, коррумпированного JSONL, параллельных writers, сетевой доставки или длительной серии стресс-сбоев. Для `ingress_uncommitted` обязательна повторная доставка источником, т.к. Core никогда не подтвердил commit. Только один прогон каждой границы на платформу; **production readiness не утверждается**.

Отдельно: `goal_latency_ms` runner измеряет **время тестового эпизода** (включая события и проверки), а не исключительно планирование/выполнение одной цели.

## Доказано

- В представленном прогоне Core v0.1 с локальным исправлением успешно исполнил сценарий ARM64 с 180 целями и 101 эффектом, сохранив проверяемые инварианты runner.
- На двух устройствах при одинаковом seed и параметрах наблюдался рост задержек с накоплением данных; причина не сводится к уникальной неисправности Raspberry.
- На обеих платформах существенная часть времени приходится на повторную загрузку/валидацию legacy EventLog; 970 из 1,010 полных чтений вызваны проверками наличия исторических Events в двух местах.
- T9.3 подтвердил примерно линейное увеличение стоимости **одного полного чтения и валидации** с ростом числа событий на Pi и PC. Обе негативные проверки EventLog завершились PASS.
- T9.4 подтвердил рост времени одного нового сквозного typed Event ingest при накоплении истории: около ×7.75/×8.08 от первой до последней 128-event группы на PC/Pi, соответственно. Инварианты приема, outbox и восьми replay сохранены в пределах harness.
- T9.5 впервые подтвердил восстановление после реального `SIGKILL` в отдельных процессах в 7 точках на Pi и PC, включая one-effect / one-operation восстановление виртуальной двери. Незафиксированный ingress event не восстанавливается без повторной доставки.
- Рост памяти процесса в этом коротком сценарии умеренный; обнаруженные bottlenecks относятся прежде всего к времени обработки, а не к исчерпанию RAM.

## Не доказано

- Точная алгоритмическая сложность всего Core, полное масштабирование семантической Memory и доля роста, вызванная отдельно EventLog, SQLite, recovery или microSD. T9.4 не измерял отдельно вклад каждого компонента.
- Скорость на одинаковых Python minor/patch versions, одинаковой ОС и дисковой подсистеме; строгий x86/ARM hardware ranking.
- Устойчивость к отключению питания, произвольным неинструментированным моментам аварии, повреждению журнала, диску с заполненным объёмом, конкурентной записи или многодневной работе. T9.5 проверяет лишь 7 контролируемых SIGKILL boundaries.
- Корректность/скорость новой experimental Memory E4, Event Retrieval C3, LLM, Godot/VAL, SLEEP и автономного L2.
- Production readiness или завершение Stage 9. Локальный патч означает, что проверялся **не чистый релизный checkout**.

## Вывод и последующие проверки

**Статус по целостности теста: PASS. T9.3 EventLog scaling: PASS. T9.4 typed Event Pipeline: PASS с измеренной деградацией latency по мере роста истории. T9.5 controlled SIGKILL recovery: PASS на обеих платформах (14/14). Статус длительного/production масштабирования и power-loss durability: OPEN; Stage 9: OPEN.** Исследование без изменений production-кода. В последующих исследовательских/разработческих сессиях допустимо отдельно спроектировать и проверить incremental raw Event lookup / durable idempotency index и оптимизацию повторных SQLite открытий, не ослабляя source integrity, provenance и recovery. До любого изменения следует выполнить baseline и негативные тесты для подмены/порчи/повторной доставки Events. Для дальнейших аппаратных измерений — повторные прогоны, фиксация точной Python-версии обеих систем, стабильных условий, повторяемые/случайные аварии и отдельный контролируемый power-loss gate (после согласования рисков и сохранения baseline).
