# Raspberry Pi 5 / PC — Core v0.1 Endurance, Profiling and EventLog Scaling (T6–T9.3)

## Цель

Проверить переносимость зафиксированного Core v0.1 на Raspberry Pi 5 (ARM64), корректность длительного синтетического прогона, сопоставить одинаковый сценарий с ноутбуком x86-64 и локализовать рост задержек без изменения production-кода. Это предварительное аппаратное исследование Stage 9, а не закрытие этапа.

## Условия

- **Core snapshot:** `6ffdc2e49b115968cb5309ea591fa27f1eace6f3`, ветка `release/core-v0.1`; `checkout_clean=false`.
- **Локальный незафиксированный патч:** `CoreDoorExecution.__init__: world: VirtualDoorWorld` → `world: DoorWorldPort`. На Python 3.13.5 исходная аннотация препятствует импорту; такой дефект был ранее воспроизведён в архитектурном обзоре от 2026-11-11. Патч не входил в указанный release snapshot; хеш изменённого дерева не представлен.
- **Raspberry:** Raspberry Pi 5, 8 GB, Raspberry Pi OS, Python 3.13.5, microSD; охлаждение и блок питания испытаны отдельно в аппаратной серии T1–T5.
- **Ноутбук:** Ubuntu, x86-64, SSD, Python 3.14.4 (GCC 15.2.0), отдельный checkout указанного snapshot; точная модель CPU и хеш локального патча не представлены. Сравнение аппаратных платформ предварительное.
- **Источник данных:** вывод терминала, переданный владельцем проекта 2026-11-12. Исходные JSON-отчёты и оба `.prof` остались на устройствах, не приложены к репозиторию; независимого повторного запуска автором этой записи не было.
- **Изоляция:** runner использует временные хранилища; Production Memory и экспериментальные E4/L2 не изменялись. GitHub production-код не изменялся в ходе данного исследования.

## Сценарий и входные данные

Runner: `scripts/run_core_endurance_gate.py`.

- **T6, ARM64 smoke:** `--episodes 24 --seed 131 --restart-every 11 --checkpoint-every 8 --blocked-goals 65`.
- **T7, ARM64 endurance:** `--episodes 180 --seed 131 --restart-every 11 --checkpoint-every 30 --blocked-goals 128`.
- **T8, x86-64 comparison:** точно те же параметры runner, что в T7.
- **T9, ARM64 profiling:** T7 под `python -m cProfile -o /tmp/anima-core-180.prof`; `pstats` сортировка по cumulative/self time.
- **T9.1, Pi caller attribution:** `pstats.Stats(...).print_callers()` для `load_events`, `_require_raw_event`, `_ensure_legacy_written`, `recover_proofs`, `_enqueue_bound_goals`.
- **T9.2, PC profiling and caller attribution:** тот же сценарий 180 эпизодов под `python -m cProfile -o /tmp/anima-pc-core-180.prof`; те же целевые вызовы и сортировка `pstats`; Python 3.14.4.
- **T9.3, отдельный EventLog scaling:** на обеих платформах отдельно создавались временные JSONL-журналы с 128, 512, 2048, 8192 и 16384 валидными синтетическими `world.observation`; для каждого размера — warm-up, семь измерений `EventLog.load_events()` с полной штатной валидацией, wall/CPU latency и размер файла. Отрицательные контроли — duplicate `ev_` ID и malformed JSON. Для Pi использован here-doc, на PC тот же бенчмарк в отдельном скрипте без изменения production-кода; код экспериментального скрипта в Git не внесён.

Пример воспроизведения (из корня checkout, с описанным локальным патчем):

```bash
.venv/bin/python scripts/run_core_endurance_gate.py \
  --episodes 180 --seed 131 --restart-every 11 \
  --checkpoint-every 30 --blocked-goals 128 \
  --report /tmp/anima-rpi-core-endurance-180.json
```

## Ожидаемый результат

Все синтетические цели завершаются с независимыми подтверждениями, без повторных/неожиданных эффектов; повторное открытие хранилищ не нарушает идентичность; заблокированные цели не мешают новым. Задержки, память и размер хранилища измеряются без заранее объявленного жёсткого SLO. Рост задержек требует отдельной диагностики и не равен автоматическому FAIL по корректности.

## Фактический результат

- **T6 Pi / 24:** отчёт создан; 24 эпизода, 14 эффектов, 2.275 с, p50/p95/p99 73.01/108.08/110.12 мс, восстановление p50/p95 29.40/30.33 мс, 65 parked goals, 0 unexpected effects, 1,008,871 B.
- **T7 Pi / 180:** `CORE_ENDURANCE_INTEGRITY_PASS goals=180 effects=101`; `CORE_SCHEDULER_BACKLOG_PASS parked=128 drains_to_new_goal=3`; `CORE_ENDURANCE_GATE_PASS`. 180 целей, 101 эффект, 17 cold reopen операций, 0 unexpected effects.
- **T8 PC / 180:** те же сообщения PASS, 180 целей, 101 эффект, 128 parked goals, 0 unexpected effects.
- **T9 Pi / cProfile:** весь integrity/scheduler/endurance gate PASS, несмотря на overhead профилировщика.
- **T9.1:** 970 из 1,010 вызовов `EventLog.load_events()` происходят из двух повторных проверок уже записанных событий.
- **T9.2 PC / cProfile:** `CORE_ENDURANCE_INTEGRITY_PASS goals=180 effects=101`, `CORE_SCHEDULER_BACKLOG_PASS parked=128 drains_to_new_goal=3`, `CORE_ENDURANCE_GATE_PASS`; 180 целей, 101 эффект, 0 неожиданных эффектов. Совпадают все ключевые количества вызовов, хотя времена отличаются.
- **T9.3 Pi / PC:** `T93_EVENTLOG_READ_PASS` и `T93_NEGATIVE_INTEGRITY_PASS` на обеих платформах. Результаты измерены для одинаковых объёмов входного файла, 7 повторов на объём.

### T9.2 — профилирование ноутбука и сравнение с Raspberry Pi

Верифицированный вывод владельца от 2026-11-12: Python 3.14.4, `cProfile` **23.334 с**, 23,092,281 вызовов (22,964,144 primitive), тогда как Pi 3.13.5 показал **34.240 с**, 21,422,891 вызовов (21,291,228 primitive). Несмотря на большее число низкоуровневых Python-вызовов в 3.14, все перечисленные ниже **значимые прикладные вызовы совпадают в количестве**. Общее число вызовов разных версий Python напрямую не интерпретируется как другая вычислительная работа.

### T9.3 — изолированное масштабирование полного EventLog read

**Источник доказательств:** сырые выводы двух командных запусков, предоставленные владельцем 2026-11-12. JSON-отчёты остаются на устройствах: `/tmp/anima-t93-aarch64.json` и `/tmp/anima-t93-x86_64.json`. Непосредственно сами JSON не загружены в Git. Тест вызывает реальный `anima.memory.event_log.EventLog.load_events()`, не меняет production-код, использует `TemporaryDirectory` и валидные ID формата `ev_<UUIDv4>`. Синтетическая запись не доказывает доверенность её `source`.

| Событий | JSONL, B | Pi wall p50, мс | PC wall p50, мс | Pi CPU p50, мс | PC CPU p50, мс | Pi / PC wall |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 128 | 61,992 | 2.876 | 2.179 | 2.874 | 2.167 | 1.320 |
| 512 | 248,616 | 11.955 | 8.462 | 11.949 | 8.439 | 1.413 |
| 2,048 | 997,210 | 49.315 | 35.113 | 49.308 | 35.002 | 1.404 |
| 8,192 | 3,995,482 | 202.408 | 147.210 | 202.379 | 146.665 | 1.375 |
| 16,384 | 8,005,948 | 412.644 | 300.652 | 412.537 | 299.807 | 1.372 |

Wall p95 на Pi: `2.954 / 16.759 / 52.449 / 223.929 / 445.110` мс, на PC: `2.504 / 9.113 / 36.102 / 149.605 / 307.542` мс для тех же размеров. **При 7 измерениях вычисляемый скриптом p95 равен максимуму выборки**, а не устойчивой оценке хвоста распределения.

Увеличение количества Events в 128 раз (128 → 16,384) увеличило медианное время полного чтения в **143.5 раза на Pi**, **138.0 раза на PC**: приблизительно линейная стоимость с небольшим ростом времени на запись. Время CPU близко к wall, что совместимо с CPU-bound JSON decode/validation в этих прогонах, но не исключает влияния кэша ОС/хранилища.

**Negative integrity gates:** на обеих машинах duplicate Event ID и синтаксически повреждённый JSON отвергнуты штатным `load_events`. Это не проверка неизменности всей истории, provenance, полномочий `source`, crash recovery или production-write path.

**Установлено:** полное чтение/валидация журнала масштабируется примерно пропорционально объёму истории на обеих машинах, а Pi медленнее в **1.32–1.41 раза** в приведённой короткой серии. В T9–T9.2 установлены 1,010 вызовов `load_events` за 180 эпизодов, из них 970 из двух legacy checks. Однако T9.3 **не изолирует вклад EventLog в задержку полного Core**, не измеряет O(N²) сквозного Event Processing и не определяет SLO для будущей ANIMA.

**Ограничения:** разные версии Python (3.13.5/3.14.4), кэш ОС, разные диски, лишь 7 повторов, единственная последовательность размеров, небольшое число отрицательных сценариев, отдельный экспериментальный скрипт не зафиксирован в Git. Для строгой регрессии потребуется закрепить точный скрипт, среды и повторить прогоны.

Отдельно: `goal_latency_ms` runner измеряет **время тестового эпизода** (включая события и проверки), а не исключительно планирование/выполнение одной цели.

## Доказано

- В представленном прогоне Core v0.1 с локальным исправлением успешно исполнил сценарий ARM64 с 180 целями и 101 эффектом, сохранив проверяемые инварианты runner.
- На двух устройствах при одинаковом seed и параметрах наблюдался рост задержек с накоплением данных; причина не сводится к уникальной неисправности Raspberry.
- На обеих платформах существенная часть времени приходится на повторную загрузку/валидацию legacy EventLog; 970 из 1,010 полных чтений вызваны проверками наличия исторических Events в двух местах.
- T9.3 подтвердил примерно линейное увеличение стоимости **одного полного чтения и валидации** с ростом числа событий на Pi и PC. Обе негативные проверки EventLog завершились PASS.
- Рост памяти процесса в этом коротком сценарии умеренный; обнаруженные bottlenecks относятся прежде всего к времени обработки, а не к исчерпанию RAM.

## Не доказано

- Точная алгоритмическая сложность всего Core, сквозного Event Processing и доля роста, вызванная отдельно EventLog, SQLite, recovery или microSD.
- Скорость на одинаковых Python minor/patch versions, одинаковой ОС и дисковой подсистеме; строгий x86/ARM hardware ranking.
- Устойчивость к отключению питания, `kill -9`, повреждению журнала, диску с заполненным объёмом или многодневной работе.
- Корректность/скорость новой experimental Memory E4, Event Retrieval C3, LLM, Godot/VAL, SLEEP и автономного L2.
- Production readiness или завершение Stage 9. Локальный патч означает, что проверялся **не чистый релизный checkout**.

## Вывод и последующие проверки

**Статус по целостности теста: PASS. T9.3 EventLog scaling: PASS (предварительно). Статус сквозного масштабирования: OPEN; Stage 9: OPEN.** Исследование без изменений production-кода. В последующих исследовательских/разработческих сессиях допустимо отдельно спроектировать и проверить incremental raw Event lookup / durable idempotency index и оптимизацию повторных SQLite открытий, не ослабляя source integrity, provenance и recovery. До любого изменения следует выполнить baseline и негативные тесты для подмены/порчи/повторной доставки Events. Для дальнейших аппаратных измерений — повторные прогоны, фиксация точной Python-версии обеих систем, стабильных условий и отдельный тест process-kill/restart.
