# Stage 1.2 SQLite Memory Store

## Цель

Подтвердить переход от временного `memories.jsonl` к локальному SQLite
`memory.db` без потери регрессии Foundation/D1. Проверяются схема Stage 1,
Memory CRUD, транзакции/rollback, reopen, ограничения, FTS5, foreign keys и
интеграция Runtime/CLI/recovery с новым хранилищем.

## Условия

Проверенный snapshot: `057f830f89ef2afe9322e4ab425a6b335a2c6da5`.
Linux, Python 3.14.4, pytest 9.1.1. Тесты используют изолированные временные
каталоги и не читают рабочие данные экземпляра.

## Сценарий

```bash
bash scripts/check.sh
.venv/bin/python -m pytest -q
.venv/bin/python -m pytest -v -s tests/test_memory.py
```

## Ожидаемый результат

- проектные проверки и вся регрессия проходят;
- `memory.db` создаётся со schema version 1;
- Memory можно создать, прочитать, обновить и удалить;
- транзакция откатывается при ошибке;
- база повторно открывается без потери записей;
- ограничения схемы и foreign keys активны;
- FTS5 отражает create/update/delete;
- невалидный SQLite-файл даёт определённую ошибку;
- D1/recovery продолжают работать уже через SQLite.

## Доказано

SQLite подходит как рабочий baseline Stage 1: схема создаётся и повторно открывается,
Memory CRUD и FTS работают, транзакции откатываются, ограничения БД применяются,
а существующий Runtime/CLI/recovery не регрессируют после замены JSONL-memory.
Связь `Memory → source Event` уже хранится через `memory_sources` и проверяется
интеграционными тестами, но полный provenance через Knowledge/Entities/Relations
относится к следующему шагу.

## Не доказано

Не доказаны Entity resolution, семантика Relations, Knowledge lifecycle,
полный `Knowledge → Memory → Event` provenance, Association, Context Builder,
idempotent processing и производительность на больших объёмах. Таблицы для этих
слоёв пока являются каркасом схемы; их поведение проверяется последующими шагами.
