# Stage 2.12 Decision Performance Baseline

## Цель

Измерить без заранее заданного SLA стоимость Stage 2 Choice для 2/10/100 Candidates
и отделить базовое ранжирование от Internal State modifiers и диагностического
`full_trace_history`. Зафиксировать baseline до будущих Fast/Agent/hardware
оптимизаций.

## Условия

Проверенный snapshot: `cae4cd06178b14df0b60e2298b9b83329066e640`.
Локальная среда владельца проекта: Linux, Python 3.14.4. Каждый размер и режим
benchmark запускаются отдельным worker-процессом. Setup БД, Goal и seed Internal
State/history выполняется до измеряемой операции. Используется ненейтральный state:
`fatigue=0.60`, `uncertainty=0.70`, `frustration=0.50`, `satisfaction=0.40`.
Raw JSON сохранён локально в `.benchmarks/stage2-decision-performance.json` и не
коммитится.

## Сценарий и входные данные

```bash
bash scripts/check.sh
.venv/bin/python -m pytest -q tests/test_decision_performance.py
.venv/bin/python scripts/benchmark_stage2.py
```

Для 2, 10 и 100 deterministic Candidates измеряются три режима: `base` — только
base-score ranking; `state_modifiers` — bounded state scoring без diagnostic trace;
`full_trace_history` — production `ChoiceEngine.choose()` с полным modifier trace и
чтением последних 20 StateTransitions. Equivalence-тест требует одинаковых final
scores и выбранного Candidate между облегчённым modifier benchmark и production
Choice Engine.

## Ожидаемый результат

- benchmark воспроизводимо проходит 2/10/100 Candidates;
- отдельно фиксируются p50/p95 wall latency и CPU latency;
- измеряются Python allocation peak и process peak RSS;
- `state_modifiers` остаётся математически эквивалентным production Choice;
- стоимость trace/history видна отдельно от самой механики выбора;
- результат служит baseline, а не SLA или поводом к преждевременной оптимизации.

## Фактический результат

Все девять комбинаций завершились успешно. Для 100 Candidates `base` дал p95
0.0211 ms, `state_modifiers` — 0.0993 ms, а полный production
`full_trace_history` — 2.0092 ms. Таким образом, сама state-модификация остаётся
субмиллисекундной с большим запасом; основная фиксированная и масштабируемая
стоимость находится в диагностическом trace/history, но даже она остаётся около
2 ms p95 на максимальном текущем наборе.

От 10 до 100 Candidates дополнительная p95-стоимость `state_modifiers` составляет
примерно 0.91 микросекунды на дополнительный Candidate, а `full_trace_history` —
около 13.2 микросекунды на Candidate поверх заметного фиксированного overhead.
CPU p95 почти совпадает с wall p95 во всех режимах, поэтому baseline выглядит
локально CPU-bound, без заметного ожидания внешнего I/O.

Candidates до 273.101 KiB на 100.

## Доказано

На текущем Python baseline Choice Engine не является bottleneck: 100 Candidates с
bounded Internal State modifiers оцениваются быстрее 0.1 ms p95, а production путь
с полным trace и bounded history — около 2.0 ms p95. Стоимость state modifiers
масштабируется умеренно и остаётся намного ниже диагностической стоимости.

Показано также, что подробная объяснимость имеет измеримую цену: на малых наборах
фиксированный overhead trace/history доминирует над самой оценкой, а на 100
Candidates растут и latency, и Python allocations. При текущих абсолютных значениях
это не требует оптимизации; baseline достаточно сохранить для будущего сравнения.

## Не доказано

Результат не является SLA и не переносится автоматически на другое железо, Python,
filesystem или будущий Planner/LLM. Не измерены тысячи Candidates, длительный
concurrent workload, многопоточность, model inference, network/tool latency и
целевое cyberdeck-железо. `Peak RSS` нельзя использовать как точную per-choice
allocation metric. Benchmark не доказывает, что trace/history никогда не станет
bottleneck при значительно более крупных Candidate sets или richer trace.
