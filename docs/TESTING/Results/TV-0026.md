# Stage 3.9 Runtime Integration

## Цель

Подтвердить интеграцию persistent SleepJob с общим lifecycle Runtime без смешивания обычного состояния `sleeping` с активной консолидацией: bounded Sleep work должен безопасно прерываться для wake, сохранять checkpoint и продолжаться после следующего входа в sleep.

## Условия

Проверенный snapshot: `155dde6720bbfe57ff38be051b45b77509933bcf`. Проверка выполнена владельцем проекта в локальном checkout.

Canonical runtime scenario проходит `wake → activate SleepJob → sleep → bounded work/checkpoint → wake/interruption → sleep/resume → complete → wake`. Дополнительно проверяются обычный sleep без Job, запрет обработки Sleep work в awake, принадлежность WorkItem активному Job и restart recovery stale `running` state.

## Ожидаемый результат

- обычный `sleep()` не создаёт и не подразумевает SleepJob;
- active SleepJob имеет lifecycle, независимый от `state.json` awake/sleeping;
- bounded обработка возвращает управление Runtime на committed checkpoint;
- wake переводит незавершённый Job в `interrupted`, не повреждая WorkItem;
- следующий sleep возобновляет Job и checkpointed WorkItem;
- terminal Job отделяется от Runtime после wake;
- stale running WorkItem/Job нормализуются через recovery Stage 3.8;
- старый Runtime/Scenario API остаётся совместимым без Sleep-конфигурации.

## Доказано

Runtime различает физическое lifecycle-состояние ANIMA и lifecycle SleepJob. Sleep processing выполняется bounded-шагами и возвращает управление на безопасной persistent границе; wake прерывает Job без потери committed chunks, а последующий sleep продолжает работу с checkpoint. Restart recovery использует уже принятый механизм Stage 3.8, а обычный sleep остаётся допустимым без активной консолидации.
