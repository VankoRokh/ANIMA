# Stage 1.10 Recovery and Idempotency

## Цель

Подтвердить persistent `event_processing`, идемпотентный replay и восстановление
после сбоев так, чтобы один raw Event не создавал повторные Memory/Relation effects,
а завершённая SQLite-транзакция оставалась согласованной с `state.json` после restart.

## Условия

Проверенный snapshot: `37ca51b26b05ae7496ce15f928f987be4aa911e2`.
Локальная среда владельца проекта: Linux, Python 3.14.4. Рабочие данные экземпляра
тестами не используются.

## Сценарий и входные данные

```bash
bash scripts/check.sh
.venv/bin/python -m pytest -q
.venv/bin/python -m pytest -v -s \
  tests/test_event_processing.py \
  tests/test_memory_processor.py \
  tests/test_recovery.py \
  tests/test_trace.py
```

Отдельный recovery corpus проверяет replay завершённого и skipped Event, fault
injection после Memory/Entity effects до commit, зависший `processing`, adoption
legacy Event, отсутствующий raw Event и рассинхрон между успешным SQLite commit и
ещё не обновлённым `state.json`.

## Ожидаемый результат

- повтор final Event не создаёт новую Memory и не меняет его attempt count;
- skipped Event остаётся final и идемпотентным;
- crash внутри Event transaction полностью откатывает Memory/Relations;
- retry после failure создаёт effect ровно один раз;
- stale `processing` обнаруживается и повторяется;
- legacy raw Events без ledger принимаются без слепой повторной обработки;
- processing record без raw Event даёт определённую ошибку;
- Runtime восстанавливает `events_processed` из final ledger после restart;
- processing допускается только для Event, уже существующего в `events.jsonl` и
  совпадающего с переданной записью.

## Фактический результат

Пользователь подтвердил `check.sh`, полный regression suite и отдельный набор
Recovery/Processor/backup/trace тестов как полностью зелёные на указанном snapshot.

## Метрики

`tests/test_event_processing.py` содержит 7 dedicated recovery/idempotency
сценариев. Performance-метрики не фиксировались: latency/CPU/RAM относятся к
Stage 1.12.

## Доказано

Memory effects одного Event и его final processing-status могут фиксироваться в
одной SQLite-транзакции. Failed/interrupted work безопасно повторяется, final Event
не размножает данные, legacy history принимается консервативно, а Runtime после
restart согласует persistent ledger с `events_processed`.

## Не доказано

Не доказаны общий end-to-end corpus Stage 1 и performance baseline на 1k/10k/100k
данных. JSONL append и SQLite commit по-прежнему не являются одной физической
транзакцией; корректность этого разрыва обеспечивается recovery protocol, а не
атомарностью между файлами.
