# TV-0042 — Stage 4.12 LLM Planner Experiment

## Цель

Подтвердить интеграцию реальной локальной модели через существующий PlannerAdapter без передачи модели authority над исполнением, безопасностью, Choice или завершением Goal. Passed означает выполнение этого интеграционного критерия, а не надёжность Qwen3-0.6B как production Planner.

## Условия

Результат относится к implementation snapshot `efa82428e986f976fefff803ae41a9db8f9555b2`. Использованы локальная Qwen3-0.6B-Q8_0 GGUF и локальный llama.cpp CPU backend, small-model profile, native constrained completion и отключённый thinking. Compact-prompt budget — 4 800 символов, output budget — 512 токенов; temperature 0.6, top-k 20, top-p 0.95, min-p 0, без фиксированного seed. Максимум — 6 Agent steps; deterministic file-content verifier — версия 2.

## Сценарий и входные данные

Canonical sandbox Goal: записать ровно `42` в `result.txt`, затем получить независимое readback evidence и позволить trusted verifier определить завершение. Каждый run начинается с отдельного свежего экземпляра.

Цепочка authority: LLM Planner proposal → Choice → Executor → Observation → replanning при необходимости → независимый readback → Verifier → завершение Goal/AgentRun. За turn исполняется не более одного выбранного Action; текст модели не является результатом Tool или доказательством успеха.

## Ожидаемый результат

Реальная LLM предлагает действия через PlannerAdapter без прямого доступа к Tool execution. Неверные действия дают фактические Observations вместо ложного success. Если Goal остаётся recoverable, Agent продолжает работу и может перепланировать. Только независимые trusted evidence, соответствующие success criterion, завершают Goal; write receipt сам по себе недостаточен.

## Фактический результат

Реальная Qwen3-0.6B вошла в production Planner path. Malformed/invalid output отклонялся до исполнения. Неуспешные read/list давали фактические Observations, которые попадали в последующие Planner turns; live replanning наблюдался. Корректные `fs.write(path="result.txt", content="42")` предлагались, выбирались Choice и исполнялись. В успешных runs последующий независимый `fs.read` возвращал ровно `"42"`, verifier v2 выдавал success, Goal и AgentRun завершались.

В ходе проверки найдены и исправлены интеграционные/контрактные дефекты:

1. Отсутствие target ошибочно трактовалось как Goal BLOCKED. Verifier v2 классифицирует unavailable readback как recoverable failure, позволяя replanning; семантика настоящего Goal blocker не ослаблена.
2. Authoritative sandbox path regex `^[^/].*$` небезопасно преобразовывался локальной реализацией llama.cpp JSON-schema-to-GBNF. ToolDescriptor validation и executor sandbox checks сохранены; только отдельная llama.cpp generation-schema projection исключает этот несовместимый pattern, не изменяя исходную схему и остальные ограничения.
3. Generation schema допускала `status="cannot_progress"` с proposals, хотя Python PlannerDecision запрещал это. Status-discriminated branches теперь требуют 1..3 proposals для `proposals_available` и 0 для `cannot_progress`; без tools доступна только вторая ветвь. Python validation остаётся независимой границей.

Это исправления интеграции и контрактов, а не улучшение самой модели.

## Метрики

Поздняя пятизапусковая current-production baseline завершила 2/5 canonical Goals. Успешные runs прошли полный путь write → independent readback → verifier success. Structured-output failures и исчерпание output-token budget оставались наблюдаемыми. Это показательный baseline в указанных условиях, а не статистически установленная общая вероятность успеха.

В отдельном временном candidate C generation schema ограничивала `rationale_summary.maxLength=256` и `expected_observation.maxLength=128`, сохраняя `plan_summary` без нового ограничения. В пяти full-AgentLoop runs C также завершил 2/5 Goals. В этой выборке C устранил run-ending structured-output failures, но неуспешные runs заканчивались step budget; часто наблюдался обрезанный advisory text. Candidate C не принят: production не содержит этих text bounds, output budget остаётся 512.

## Доказано

- Реальная локальная LLM может быть заменяемой реализацией Planner.
- Смена Planner backend не требует передачи authority Tool/Choice/Verifier модели.
- Предложения проходят authoritative validation; malformed или противоречивый output отклоняется до исполнения.
- Фактические failed-action evidence доступны следующим Planner turns; live replanning работает.
- LLM-driven AgentRun может завершить canonical task, причём завершение требует независимого verified evidence.
- Model/backend latency и token information доступны для наблюдения.

## Не доказано

Stage 4.12 не доказывает надёжность Qwen3-0.6B как production Planner, детерминированный или высокий canonical success rate, широкую генерализацию задач, длительную автономную работу, оптимальность prompt/schema/sampling, пригодность performance для конечного hardware, превосходство candidate C или одной модели/размера/provider над другими.

Известные ограничения baseline: stochastic planning quality, повторные reads/lists и задержанные corrective actions, verbose free-text generation, occasional output-token exhaustion и hypothetical/fabricated expected-observation details модели. Такие details являются advisory proposals, а не фактическими Tool Observations.

Отдельный follow-up, не блокирующий Stage 4.12: технически успешное действие может получить CandidateHistory failure semantics, пока Goal verification отражает более старое negative evidence. Action outcome и Goal-verification outcome следует исследовать отдельно.
