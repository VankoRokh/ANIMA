# Stage 3.13 End-to-End Validation

## Цель

Подтвердить Stage 3 как единый рабочий контур, а не набор изолированных механизмов: реальные Event/Memory/Knowledge источники должны проходить bounded selection, consolidation, interruption/restart/resume и завершаться derived result с provenance без повторных эффектов. Отдельно проверить тот же checkpoint/resume contract на synthetic large source.

## Условия

Проверенный snapshot: `f062f8e91fb7f28a854682d55c0d317846a45bb9`.

Перед финальной валидацией был устранён lifecycle-дефект resource-budget пути: повторный вызов `process_work()` при уже исчерпанном budget больше не создаёт пустой переход `checkpointed → running → checkpointed`. Отдельный regression-тест защищает это поведение.

Проверки выполнялись на production-компонентах Stage 1–3 с локальными тестовыми данными и synthetic large source; владелец проекта подтвердил успешное прохождение всех указанных ниже команд.

## Сценарий и входные данные

### Text / cognitive sources

Сценарий использует production-компоненты `EventLog`, `MemoryStore`, `KnowledgeLayer`, `SleepSelector`, `DeterministicTextConsolidationProcessor`, `SleepChunkExecutor` и `DerivedResultRepository`.

Проверяются:

- raw Event;
- CLOSED Memory с provenance;
- CONFIRMED Knowledge с supporting evidence;
- OPEN Memory и provisional Knowledge как неeligible sources;
- deterministic bounded selection;
- interruption после committed chunk;
- reopen `sleep.db` как имитация restart;
- resume со следующего незавершённого chunk;
- эквивалентность допустимого результата uninterrupted и interrupted/resumed run;
- derived authority и processor/version;
- provenance до исходного source;
- неизменность Event/Memory/Knowledge источников;
- replay завершённой работы без создания второго derived result.

### Large source

Synthetic Asset логического размера 10 GiB проходит тот же chunk/checkpoint contract. Работа прерывается на произвольной безопасной границе, после reopen начинается direct resume с ожидаемого sequence; `sleep.db` хранит только metadata/checkpoints/results, а не полный payload.

Команды финальной проверки:

## Ожидаемый результат

Targeted и полный regression suite проходят; uninterrupted и interrupted/resumed Sleep дают эквивалентный допустимый итог; restart/replay не повторяют committed logical effect; derived result сохраняет processor/version и полный provenance; исходные Event/Memory/Knowledge не изменяются скрыто; synthetic 10 GiB source обрабатывается через bounded chunks без хранения полного payload в `sleep.db`.

## Фактический результат

Все targeted Stage 3.13 проверки, ключевой Sleep regression contour, полный project regression suite и `scripts/check.sh` прошли успешно на указанном snapshot.

Финальная Stage 3.13 validation использует функциональные pass/fail критерии и не вводит новый performance SLA. Resource/performance baseline Stage 3 зафиксирован отдельно в TV-0029; large-data validation использует synthetic source логического размера 10 GiB. Для TV-0030 ключевыми метриками являются отсутствие повторного logical effect после replay/restart, сохранение provenance и успешное прохождение targeted и полного regression suite.

## Доказано

Stage 3 выполняет заявленный контракт целиком: Sleep детерминированно отбирает bounded workload, обрабатывает заменяемым processor, сохраняет persistent checkpoint и derived provenance, безопасно переживает interruption/restart, не повторяет уже committed logical effect и остаётся пригодным для источников, размер которых существенно превышает RAM.

Runtime lifecycle, observability/resource budget, recovery/idempotency, large-data readiness и performance baseline не противоречат друг другу при совместном использовании.
