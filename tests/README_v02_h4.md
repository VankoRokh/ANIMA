# ANIMA v0.2 — H4 / Entity & Episode Association: conservative guard

**Статус:** рабочий кандидат в отдельной ветке, **не принят без запуска тестов и quality probe на ноутбуке**.

**Ветка:** `work/v02-h4-identity-guard`, основана на H3 (`1888 passed, 2 xfailed`, по результатам владельца).

**Основание:** R1-S1 N1/N2 и контрольные отрицательные сценарии лаборатории M-T2C C1/C3/C4/C5 (не свободная семантика).

## Контракт H4.1: существование Entity != подтверждённая связь

В `Event.references` передаются только `{kind,id}`, без подписи, версии источника, claim-specific evidence или делегированного полномочия. Следовательно `MemoryProcessor` **не может** выдавать проверенную связь с Entity на одном факте существования ID.

Консервативное поведение production:
- Неизвестный Entity ID — `ValueError`, без создания производной Memory.
- `inactive/merged` Entity ID — `ValueError`; не публикуется текущий `about`.
- Существующий `active` Entity ID — типизированная **неподтверждённая заявка** в неизменяемом Raw Event. `MemoryProcessor` НЕ создаёт автоматически `about` и не добавляет `entity_overlap` в score на основании `Event.references`.
- Запись `Event.references` остаётся частью `EventLog` для последующей ручной/отдельной проверки. **Новое API утверждения/авторизации Entity не добавлено**, схема SQLite не меняется.
- Низкоуровневый `LinkStore.create_relation(about)` остаётся отдельной явно инициированной операцией. Он **не проводит** криптографической или семантической проверки полномочий вызвавшего компонента; этот риск нельзя объявлять решённым глобально.

Особенно важный отрицательный сценарий: сообщение о Vega с указанным зарегистрированным **active Orion** не превращается автоматически в `about Orion` (это более строгая проверка, чем только отказ для `inactive` Orion).

## Контракт H4.2: несовместимые claims не смешиваются

Для новой association проверяются наборы Entity IDs **каждого Raw Event-источника** кандидатной Memory. ID-набор может использоваться только как основание **запретить** слияние, но не как положительное свидетельство.

- Разные указанные ID-наборы → **не** делать `update`, даже при совпадении текстового шаблона, времени и сессии.
- Если есть явная заявка у одной стороны и отсутствует у другой, **не** наследовать идентичность и не сливать события.
- `{A,B}` ≠ `{A}` и ≠ `{B}`: многосубъектный Event не становится мостом между отдельными историями.
- Для двух Events без Entity references прежняя лексическая эвристика сохраняется; это НЕ гарантирует корректную группировку, если в тексте упоминаются разные субъекты.
- Одинаковый неподтверждённый Entity ID сам по себе **не** является положительным основанием для `update`. Если сильное текстовое сходство есть, `update` может остаться допустимым.

Выбор консервативный и намеренно повышает вероятность **false split**. Разрешение и последующая безопасная консолидация отдельных эпизодов сейчас **не реализуются**.

## H4.3: граница качества и историческая совместимость

Добавлены:
- `tests/test_v02_h4_identity_guard.py`: 9 тестов связей, active/unknown/inactive IDs, многосубъектного моста, raw provenance, запрета Entity-only merge и сохранения подходящих лексических совпадений.
- `tests/test_v02_h4_m_t2c_regressions.py`: 4 сценария, основанных на исходной лаборатории M-T2C: C1 с пропусками refs, C3 с отдельными субъектами, C4 с зарегистрированным ложным ID, C5 с несколькими субъектами. Проверяют конкретные известные false merges; не заявляют автоматическую истину Entity.
- `tests/bench_v02_h4_identity_quality.py`: **четыре синтетические пары**, измеряются `false_merge_pairs`, `false_split_pairs`, pairwise precision/recall. По задумке контракта может остаться 1 false split на паре с общей заявкой без пересечения текста; это явная цена отказа от ложной идентификации.
- H0 N1/N2 теперь обычные `PASS`; оставшиеся сценарии H0 тоже должны быть PASS — `XFAIL` больше не планируется.

Существующие тесты `test_memory_processor.py` и `test_event_processing.py` обновлены **по изменившемуся контракту** (нет автоматического `about`, нет Entity-only association). Эксперимент `EXP-009` продолжает использовать текущий `MemoryProcessor` под историческим именем `legacy_64/legacy_512`; его прежние результаты на v0.1 **нельзя** считать результатами повторного прогона на H4. Автоматический production Shadow НЕ включается.

**Существенное ограничение:** N1/N2 в проверенных входах закрываются посредством conservative fail-closed. Это **не** означает решения semantic identity, автоматического извлечения сущностей из свободного текста или проверки правомочности прямых `LinkStore` вызовов. Legacy `about`, уже существовавшие в старых базах, не очищаются и не переписываются без отдельного аудита. Продолжение Memory без refs остаётся эвристическим.

## Запуск на ноутбуке

Из корня проекта:

```bash
git status --short
git rev-parse HEAD

PYTHONPATH="$PWD" .venv/bin/python -m pytest -q -rx \
  tests/test_v02_h0_foundation_contracts.py \
  tests/test_v02_h4_identity_guard.py \
  tests/test_v02_h4_m_t2c_regressions.py \
  tests/test_memory_processor.py \
  tests/test_event_processing.py \
  tests/test_memory_shadow_encoding.py \
  tests/test_memory_association_guard.py
```

Затем:

```bash
PYTHONPATH="$PWD" .venv/bin/python -m pytest -q
```

**Ориентир полного прогона:** `1903 passed`, **0 XFAIL** (1888 ранее PASS + 2 исправленные XFAIL + 13 новых тестов). Это **не измеренный результат**. Счётчик не является доказательством правильности; любые отклонения разбирать по первичной причине.

Синтетическое качество:

```bash
PYTHONPATH="$PWD" .venv/bin/python tests/bench_v02_h4_identity_quality.py
```

В benchmark `precision/recall` относятся только к четырём заранее зафиксированным парам, не к реальным потокам. Содержимое каждого Event и его refs должно оставаться неизменным. Повторный полный M-T2C эксперимент и оценка фрагментации на расширенном корпусе рекомендуются в H5.

## Критерии приёмки

1. N1/N2 обычный PASS, общая регрессия без FAILED/ERROR/XPASS.
2. C1/C3/C4/C5: нет ложного утверждения `about` или известных cross-object Memory merges.
3. Raw EventLog и идентификаторы сохранены; lifecycle H1–H3 не регрессирует.
4. Quality probe выдаёт наблюдаемое число false merges/splits; увеличение false splits **документировано**, а не скрыто.
5. Независимый H5 audit повторно оценит остальную поверхность Entity authority и legacy данных до v0.2 Release Candidate.

**Никакого автоматического удаления Raw, миграции пользовательской Memory, LLM, production Shadow или Raspberry Pi gate в H4.**
