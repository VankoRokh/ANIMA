# ANIMA v0.2 — H1.3 / Indexed Raw Prefix Integrity

**Статус:** рабочее исправление и проверки внесены в отдельную ветку; фактический прогон на ноутбуке ещё не проведён.

**Ветка:** `work/v02-h1-index-prefix-verification` (продолжает H1.1 и H1.2).

**Основание:** R1-S1 N6. При изменении записи в середине проиндексированного JSONL и последующем append контроль только head/tail anchors не обнаруживал изменения; `sync()` мог сообщить `complete` с устаревшей FTS-выдачей.

## Исправление

В `EventRetrieval.sync()`, **перед добавлением записей из увеличившегося источника**, проверяется весь ранее проиндексированный префикс:

- читается один JSONL-ряд за раз;
- каждый непустой ряд сравнивается со следующим локатором `indexed_events` по `raw_offset`, `raw_length` и SHA-256 сохранённых исходных байтов;
- пустые строки пропускаются, но новая непустая строка на их месте вызывает несовпадение;
- отсутствие/перестановка индексных строк или изменённые данные вызывают `ValueError(... rebuild required)`;
- при несовпадении транзакция откатывается, курсор и индекс не продвигаются.

**Никакого автоматического восстановления или удаления исходного журнала.**

Использована существующая схема SQLite; новых колонок нет. Изоляция `BEGIN IMMEDIATE` сохранена.

## Что намеренно не заявляется

1. Это защита от N6 при `sync()` в случае роста журнала, а **не криптографически защищённый от враждебного изменения источник истины**. Запись и DB, которые злоумышленник может согласованно подменить, данным слоем не защищены.
2. `EventRetrieval.status()` остаётся быстрым метаданным индикатором; он не проверяет содержимое среднего сегмента журнала на каждом вызове. Точечные `get/search` проверяют байты найденных событий, но не осуществляют полный аудит отрицательной выдачи.
3. Байты пустых JSONL-разделителей не хранятся в `indexed_events`; существенные события проверяются по locators/digests, а изменение одного пустого разделителя на другой допускается.
4. Гарантии H1.1/H1.2 по Recovery и завершённым Event ID продолжают действовать. Полная сверка **содержимого** уже финализированных событий по состоянию SQLite не входит в H1.3.
5. Автоматический `rebuild()` после обнаружения ошибки **запрещён**: он может принять повреждённые Raw за новые исходные данные. `rebuild` допустим только после самостоятельной проверки и подтверждения доверия к текущему источнику.

## Производительность — обязательная часть приёмки

Проверка старого префикса **линейна по количеству ранее индексированных событий** при каждом росте журнала с последующим `sync()`. Повторной полной проверки нет при продолжении порционного индексирования **физически неизменённого** файла; при изменении метаданных исходного файла перед продолжением индексирования старый префикс перепроверяется. Она не выполняется при точечном `get/search` поверх неизменённого источника.

Это корректностный компромисс, **не утверждение о приемлемой производительности**. Запрет на незамеченное повреждение не должен приводить к неприемлемому времени работы при крупном EventLog.

Отдельный вспомогательный benchmark (не входит в обычный pytest) создаёт только временные файлы:

```bash
PYTHONPATH="$PWD" .venv/bin/python \
  tests/bench_v02_h1_3_index_prefix.py --events 1000 10000 50000
```

Он выводит `unchecked_append_sync_ms` (внутренний одноразовый замер без новой проверки) и `verified_append_sync_median_ms`. Указанный в benchmark обход проверки **никогда не следует применять к реальному экземпляру**.

Если увеличение задержек при 10k–50k Events существенно для целевой нагрузки, **не принимать H1.3 в предложенном виде**. Тогда потребуется пересмотреть доказательство неизменности префикса или протокол index/source, сохранив строгий отказ при обнаруженном нарушении.
