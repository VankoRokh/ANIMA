# ANIMA v0.2 — H1.3 / Indexed Raw Prefix Integrity (optimized candidate)

**Статус:** ✅ **H1.3 принято по результатам владельца**: 1840 PASS, 6 XFAIL за 85,95 с; повторный benchmark подтверждён. Данные относятся к оптимизированной H1.3 (commit `4376d73a4512753865b9484ef4d15c9a63534780`).

**Ветка:** `work/v02-h1-index-prefix-digest`, основана на работающей H1.3 (`work/v02-h1-index-prefix-verification`). Исходные H1.1/H1.2 сохранены.

**Основание:** R1-S1 N6. Старые head/tail anchors не обнаруживали исправление одной записи в середине индексированного JSONL с последующим append.

|---:|---:|---:|---:|

Сокращение времени при 50 000 Raw Events — около 78%. Дополнительное чтение остаётся O(размеру индексированного префикса) и является документированным ограничением. Не считать это стресс-тестом непрерывной работы, подтверждением физических отключений питания или гарантией производительности на больших журналах.

## Почему пришлось оптимизировать

Предыдущая H1.3 успешно прошла `1831 passed, 6 xfailed`, но benchmark пользователя показал:

| Raw Events | Unchecked append sync | Verified append sync | Overhead |
|---:|---:|---:|---:|
| 1 000 | 1.407 ms | 8.335 ms | 6.928 ms |
| 10 000 | 1.023 ms | 40.239 ms | 39.216 ms |
| 50 000 | 1.395 ms | 214.331 ms | 212.936 ms |

Эти результаты относятся **только к прежней реализации** с проверкой каждой записи через SQLite. Они не доказывают скорость нового алгоритма.

## Новая реализация

- В `event_index_state` добавлены два поля **производного индекса**: `prefix_digest TEXT` и `indexed_count INTEGER`. Миграция автоматически добавляет отсутствующие столбцы; `memory.db`, Raw JSONL и идентификаторы Event не изменяются.
- `prefix_digest` = SHA-256 байтов JSONL от начала файла до подтверждённого `cursor`, включая переводы строк и пустые разделители. Проверка предыдущего префикса при изменении источника теперь использует потоковые блоки по 1 МиБ, вместо индивидуальных SELECT/сравнений 50 000 строк.
- `indexed_count` сопоставляется с текущим числом строк `indexed_events` для обнаружения потери локатора. Контроль содержимого произвольно изменённой, но неизменно большой SQLite-таблицы **не является** целью данного digest; необходимо ограничивать несанкционированную запись в индекс.
- При первом открытии старого индекса без `prefix_digest` **сначала** проверяются каждый прежний локатор и hash Event (существующий метод `_verify_indexed_prefix`), и только затем вычисляется/фиксируется `prefix_digest`. Новый digest не должен узаконивать историческую порчу.
- В одном `EventRetrieval` кешируется промежуточное состояние хеширования для порционной догрузки **неизменённого** файла. При изменении идентичности, размера или метаданных файла кеш не используется: старый префикс сверяется по сохранённому digest.
- После каждого успешного sync SQLite фиксирует новые cursor, digest, indexed_count и anchors в одной транзакции. Никакого переписывания Raw Events нет.
- При обнаружении несовпадения возвращается ошибка `rebuild required`, операция откатывается. `rebuild` допустим только после отдельной проверки доверия к текущему журналу.

## Пределы гарантий

1. `status()` остаётся **метаданным** индикатором и не хеширует файл при каждом вызове.
2. Сверка внешне изменённого исходника выполняется при `sync()`, не при каждом `get/search`. Хешам требуется доверенное хранение состояния SQLite; согласованная враждебная подмена исходника и индекса этим способом не обнаруживается.
3. Нельзя приравнивать этот подход к безопасному Retention и восстановлению после реального выключения питания. Отдельно остаются durability (`fsync`), cross-file transactions и N9 для других версий обработчиков.
4. Проверка агрегированного хеша всё ещё **O(bytes)** при изменившемся файле. Оптимизация устраняет дорогостоящий цикл по SQL-локаторам, но не делает проверку постоянной по времени.
5. Отказ после обнаружения повреждения остаётся строго **fail-closed**: никакой автоматической обрезки или «ремонта» Raw не выполняется.
