## Цель

Нельзя превращать недействительные `supports` в подтверждённое Knowledge и нельзя удалять Memory, если после удаления останутся осиротевшие отношения или исторические свидетельства.

## Исправление 1: переходы Knowledge

В `KnowledgeLayer.confirm()` и `KnowledgeLayer.reject()` вместо простого количества `supports/contradicts` применяется проверка действительности свидетельств **на момент перехода**.

Отношение считается пригодным только если:
- его источник — именно `memory`, а `source_id == source_memory_id`;
- соответствующая Memory существует и имеет статус **CLOSED**;
- свидетельство уже создано к моменту перехода;
- `valid_until` ещё не наступило (значение `NULL` или конечная дата позже перехода);
- статус/данные Memory уже были актуальны к моменту подтверждения;
- та же Memory не имеет одновременно активного `supports` и `contradicts` для того же Knowledge.

При недействительном *активном* свидетельстве или отсутствии хотя бы одного действительного свидетельства — **ValueError**, откат SQLite-транзакции; не создаётся новый финальный статус.

**Совместимость:** `challenged` Knowledge может быть повторно подтверждено новой закрытой Memory, даже если остаётся действующее `contradicts` от **другой** Memory. Это сохраняет существующий lifecycle и не стирает историю. Истёкшие или ещё не наступившие отношения не засчитываются.

Важно: это проверка пригодности `Memory` и `Relation` к переходу, **не глобальная гарантия достоверности содержимого Memory** и не проверка первичного Raw Event непосредственно из `KnowledgeLayer`. Полный аудит ранее подтверждённых Knowledge отдельно нужен; существующие объекты не модифицируются при открытии.

## Исправление 2: удаление Memory

`MemoryStore.delete_memory()` теперь выполняет под `BEGIN IMMEDIATE` проверку зависимостей и **отказывает в удалении** при наличии:

- любой (включая историческую/истёкшую) связи `relations` с Memory в роли источника, цели или `source_memory_id`;
- `knowledge_sources` (legacy), `memory_entities` (legacy);
- записей `history`, которые ссылаются на Memory либо принадлежат её истории;
- другой Memory с `merged_into`, указывающим на удаляемую.

Свободная Memory без таких зависимостей по-прежнему может быть удалена (для обратной совместимости). Удаление не реконструирует, не каскадирует и не вычищает исторические свидетельства. Тест N4 переведён в обычный PASS.

В `LinkStore.create_relation()` ссылки повторно проверяются внутри **того же типа writer-lock**, что используется при удалении; это закрывает гонку публичных путей создания Relation и удаления Memory между первоначальной проверкой ID и INSERT.

**Ограничение:** прямые SQL-записи в `relations` и `memories` могут обойти защиту Python API, так как у полиморфных relations нет внешнего ключа; внепроцессный неконтролируемый доступ к `memory.db` должен быть запрещён. Существующие повреждённые legacy базы не исправляются автоматически.

- Уже существующие `confirmed` Knowledge со старыми сомнительными источниками не изменяются без отдельного аудита/миграционного решения.

- Никаких новых функций памяти, автоматических Retention/SLEEP и Raspberry Pi gate в рамках v0.2.

**Критерий приёмки:** N4 PASS, все 22 новые проверки PASS, все исходные Knowledge-тесты PASS, полная регрессия без FAILED/ERROR/неожиданных XPASS. При расхождении результатов устраняем причину, не изменяя правила ради зелёного счётчика.
